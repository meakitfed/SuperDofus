# Architecture du client SuperDofus

## L'idée en une phrase

Le client ne parle **jamais** directement à la logique de jeu. Il passe toujours par une **API de messages** (`GameBackend`), et cette API peut se brancher à deux endroits.

```
                      ┌──────────── client (Godot, nœuds) ────────────┐
 clics, clavier ───►  │ ClientSession ─► MapView / ActorView / GroupView │
                      └───────┬─────────────────────────────▲──────────┘
                     send(cmd)│                             │ signal event(ev)
                      ┌───────▼─────── GameBackend ─────────┴──────────┐
                      │ LocalBackend  (standalone : sim dans le process) │
                      │ RemoteBackend (plus tard : WebSocket + JSON)     │
                      └───────┬──────────────────────────────▲─────────┘
                              │ mêmes messages JSON          │
                      ┌───────▼──── WorldSim (sim/) ─────────┴─────────┐
                      │ maps, acteurs, IA des monstres, règles         │ ◄─ WorldSource (données du monde)
                      └────────────────────────────────────────────────┘
                shared/ : géométrie, pathfinding, timing, protocole (utilisé des deux côtés)
```

- **Standalone** : `LocalBackend` embarque `WorldSim` dans le client. Il n'y a ni réseau ni serveur : c'est un jeu hors ligne complet, et c'est le mode de dev par défaut.
- **Serveur** (pas encore écrit) : un `RemoteBackend` envoie exactement les mêmes messages à un serveur, qui fait tourner le même `sim/`. Rien d'autre ne change côté client.
- **Pourquoi** : on développe tout le jeu, IA comprises, sans serveur. Les agents testent la logique en headless (`sim_cli`, tests) sans fenêtre. Quand le serveur arrive, on migre sans réécrire le client.

## Les couches (`game/src/`)

| Dossier | Rôle | Peut dépendre de |
|---|---|---|
| `shared/` | `DataFiles` (seule lecture de fichiers autorisée : données statiques, en lecture seule), `MapGeometry` (cellules Dofus 14×20), `MapData`, `MapPathfinder` (A*), `Movement` (durées des pas, interpolation, `replan`), `FightRules`, `ItemEffects` (effets d'objet : jets à la création, effets d'utilisation), `CriteriaEval` (le seul lecteur des conditions Dofus `criterions`), `Equipment` (emplacements, bonus des objets et des panoplies, coup d'arme), `StatFormulas` (caractéristiques : paliers de capital, stats dérivées), `SpellBook` (sorts de toutes les classes : grades par niveau, paires de variantes, disposition de la barre), `GameData` (table d'XP, objets), `NameRules` (règles de nom Dofus, aussi utilisées par le client pour valider en direct), `LookBuilder` (look d'un personnage depuis classe, sexe, corps, visage et couleurs : validé par la sim, prévisualisé par l'écran de création), `Protocol` | rien (+ `IsoGrid`) |
| `sim/` | **autoritaire, = futur serveur** : `WorldSim` (routeur fin : connexion, tick, drain, dispatch des commandes ; voir « Découpage de `WorldSim` » plus bas), `MapInstance`, acteurs, `Character` (personnage persistant), `GameSession` (une connexion : choix du personnage puis jeu), `CharacterRoster` (liste, création, suppression des personnages d'un compte), `Persistence` (interface de stockage, implémentation mémoire), `Clock` (date réelle, manuelle par défaut), `ai/`, `fight/` (`Fight`, `Fighter`, `Buff`, `FightEffects`, `FightAI`, `FightRewards`), `WorldSource` | `shared/` uniquement |
| `api/` | les hôtes : `GameBackend` (interface), `LocalBackend`, `LocalServer` (héberge un `WorldSim` par monde, partageable entre plusieurs backends), `FilePersistence` (`user://saves`), `SystemClock` | `sim/`, `shared/` |
| `client/` | nœuds Godot : `ClientSession` (séquenceur d'événements), `MapView`, `ActorView`, `GroupView`, `CharacterSelectScreen` (choix du personnage), `CharacterCreationScreen` (création : classes, sexe, corps, visage, couleurs, aperçu animé), `PlayerHud` + `CharacteristicsWindow` (C) + `InventoryWindow` et `EquipmentWindow` (I) + `SpellBookWindow` (S, grimoire) + barre de sorts, `ui/` (le kit d'interface, voir plus bas), `fight/` (`FightView`, `FightHud`, `TimelineTile`, `FightResultWindow`, `SpellFx`) | `api/`, `shared/`, addon `dofus_renderer`, `presentation/AnimMap` |
| `addons/dofus_renderer` | rendu des entités (voir README) | rien |
| `domain/`, `world/`, `presentation/` | démo iso héritée (`scenes/demo`). `IsoGrid` et `AnimMap` sont réutilisés | — |

Les règles, vérifiées par `tests/test_architecture.gd` :
1. `shared/` et `sim/` sont de la **logique pure** : `RefCounted`, sans aucun `Node`, `Input` ni rendu, et sans référence à `api/` ou `client/`. Elles doivent pouvoir tourner dans un serveur headless.
2. `client/` n'appelle **jamais** `sim/`. Tout passe par `backend.send()`, le signal `backend.event` et `backend.time_ms()`.
3. Les messages sont des `Dictionary` JSON-safe. Après JSON, un nombre revient en **float** : il faut donc toujours appliquer `int()` à la lecture. `LocalBackend.serialize_messages` (activé par défaut) fait l'aller-retour JSON pour que les erreurs apparaissent dès le mode standalone.
4. La sim est **déterministe** pour une seed donnée : pas de `randf()` global, chaque map a son `RandomNumberGenerator`.

## Protocole (`shared/protocol.gd`)

La référence complète (tous les messages, leurs champs, les codes d'erreur) est **`docs/PROTOCOL.md`**, générée depuis `Protocol.SCHEMA` par `tools/protocol_doc.gd`. Un test échoue si elle n'est plus à jour.

- **Schéma** : `Protocol.SCHEMA` est la source unique. La sim valide chaque commande (`WorldSim.handle`, donc côté serveur aussi) avant d'appliquer les règles. `LocalBackend` vérifie chaque événement en test (`LocalBackend.schema_errors`).
- **Version** : `hello.v` doit valoir `Protocol.VERSION`, sinon `error{code: version}` ; `welcome.v` la renvoie.
- **Enveloppe** : les commandes sont numérotées `seq` par le backend (`GameBackend._stamp`), et les événements par la sim, par session (`WorldSim.drain`). Une erreur porte `ref`, le `seq` de la commande refusée.
- **Erreurs typées** : `error{code, msg, cmd, ref?}` avec les constantes `Protocol.E_*`. Les règles renvoient ces codes. Le client les traduit (`client/error_texts.gd`) et les affiche dans un toast (`client/ui/toast.gd`). `msg` n'est qu'un détail technique en anglais.

Client → jeu :
- `hello{v, world, name, look}` : se connecter à un monde ;
- `move{cell, run}` : c'est la sim qui calcule et valide le chemin ;
- `change_map{dir}` : accepté seulement si le joueur est sur (ou va vers) une cellule de sortie de ce côté (`MapData.can_exit`, d'après `cellsData.mapChangeData`) ;
- `use_trigger{cell}` : prendre la porte ou l'escalier de la cellule `cell` (`MapData.triggers`), depuis cette cellule ou une voisine ;
- `use_zaap` (réponse `zaap_list`), `zaap_travel{map}`, `set_save_point` : le joueur doit être à côté du zaap de la map (`MapData.use_cells(zaap)`) ;
- `use_item{uid}` (consommable, hors combat) et `destroy_item{uid, qty?}` ; `equip{uid, slot}` / `unequip{slot}` (hors combat) ;
- `boost_stat{stat, points?}` : dépenser jusqu'à `points` de capital au coût du palier (hors combat) ; `reset_stats` : tout remettre à 0 et récupérer le capital ;
- `fight_attack{group}`, `fight_place{cell}`, `fight_ready{ready}`, `fight_move{cell}`, `fight_cast{spell, cell}`, `fight_end_turn`, `fight_leave` : voir la section Combat.

Jeu → client :
- `welcome{v, you, time, world}` ;
- `map_enter{map, actors}` ;
- `actor_add{actor}` ;
- `actor_remove{id}` ;
- `actor_move{id, path, t0, run}` ;
- `error{code, msg, cmd, ref?}` ;
- `inventory{items}` à la connexion, puis `item_added{item}` (pile nouvelle ou changée) et `item_removed{uid}` ;
- `player_stats{stats}` : le personnage (niveau, XP, kamas, capital, caractéristiques, PV, pods, sorts connus), envoyé à la connexion, après un combat et après un `boost_stat`. Les PV se régénèrent hors combat : `hp(t) = min(max_hp, hp + (t − hp_t0) / regen_ms)`, calculé par le client comme un mouvement ;
- `fight_start`, `fighter_placed`, `fighter_ready`, `fight_begin`, `fight_turn`, `fighter_move`, `spell_cast`, `fight_end` : voir la section Combat. Le détail des dictionnaires (combattant, buff, effet, récompense) est en tête de `protocol.gd`.

Format d'un acteur : `{id, kind: "player"|"monster_group", name, cell, dir, looks: [look strings], move?}`.

**Mouvement (modèle Dofus).** Le serveur envoie le chemin complet et son instant de départ `t0`, sur l'horloge du jeu en ms. Le client l'anime avec `Movement.sample(path, t0, run, backend.time_ms())`, c'est-à-dire le même code que celui avec lequel la sim calcule l'arrivée. Quand un acteur change de cible en cours de route, `Movement.replan` fait finir le pas en cours puis enchaîne le nouveau chemin, sans téléportation.

**Changement de map (modèle Dofus).** Les cellules de bord mènent à la map voisine :
- gauche : `col == 0` ;
- droite : `col == 13` ;
- haut : `row <= 1` ;
- bas : `row >= 38`.

Une cellule de bord n'est une sortie que si son `mapChangeData` (données de la map Dofus, bit i = direction Dofus i, 0 = est, sens horaire) contient un bit de ce côté : droite 7, 0, 1 ; bas 1, 2, 3 ; gauche 3, 4, 5 ; haut 5, 6, 7 (`MapData.SIDE_BITS`, `exit_dirs`). Deux maps voisines dans les données peuvent n'avoir aucune cellule de passage (falaise). Une map sans `map_change` (mondes générés) garde l'ancienne règle : tout le bord.

Le client marche jusqu'à la cellule de sortie, puis envoie `change_map`. La sim place alors le joueur sur `MapGeometry.mirror_cell` si elle ramène d'où il vient, sinon sur la cellule la plus proche qui ramène, sinon sur la cellule libre la plus proche (`MapData.arrival_cell`). Portes et escaliers (P1.07b) : `MapData.triggers` (cellule → `{to_map, to_cell}`). La cellule est celle de l'élément interactif dans la map du client (`m_interactionId` + `cellId`) ; la destination est une donnée serveur, lue dans les dumps JondoEmu par `tools/extractor/jondo.py` (lignes Giny 2.68 rattachées à l'élément, sinon le graphe du monde 2.73, dont l'arrivée est la porte retour), et gardée seulement si l'élément est bien sur cette cellule. `maps.py world_doors` ajoute au monde les intérieurs de la zone atteints par une porte sans condition, et écarte ceux qui n'ont pas de porte de sortie. `links.json` peut encore ajouter ou corriger une porte. Comme tout élément interactif, une porte s'utilise depuis sa cellule ou une cellule voisine (`use_cells`) ; le client marche à côté puis envoie `use_trigger` (`MapData.door_near` : la porte ou une cellule bloquée qu'elle couvre). Tous les déplacements de map passent par `WorldSim.teleport` (bords, portes, potion de rappel, zaaps). `map_enter.map` porte `subarea`, `area`, `area_name_id`, `outdoor`, `coords`, `map_change` et `triggers` ; le client affiche « Zone - Sous-zone » et les coordonnées en haut à gauche, éclaire la cellule de sortie survolée et fait un fondu au noir au changement de map.

**Zaaps et point de sauvegarde (P1.08).** `MapData.zaap` = cellule du zaap (les maps viennent de la table `waypoints`, la cellule de `links.json`, APPROX). Un élément interactif s'utilise depuis une cellule marchable voisine (`MapData.use_cells`). Le zaap s'enregistre en entrant sur sa map (`Character.known_zaaps`, événement `zaap_known`, APPROX) ; `player_stats.zaaps` = `[{map, coords, name_id, area_name_id, world_map}]` (la sim remplit `Character.zaap_info` depuis les données du monde : le client ne lit jamais le monde). Prix : `shared/Travel.zaap_cost` (10 × partie entière de la distance en ligne droite, ÷ 4 depuis Incarnam, source : wiki Dofus). `WorldSim.save_point` sert à la potion de rappel et à la défaite (1 PV). Client : `ZaapWindow` (destinations, prix, Voyager, Sauvegarder), clic sur le zaap = marcher à côté puis `use_zaap` ; `WorldMapWindow` (M) et la minimap (en haut à droite) utilisent `ui/WorldMapView` : les vraies tuiles de la carte du monde (`maps.py worldmap <id>`, table `worldmaps` : pixel de la map x, y = `origineX + x·mapWidth`, `origineY + y·mapHeight`), la map du joueur, les zaaps connus, le point de sauvegarde.

**Groupes de monstres.** La sim ne gère qu'**un** acteur par groupe (le chef), mais elle transmet tous les looks du groupe. Les suiveurs sont purement visuels, comme dans Dofus : c'est `GroupView` qui les place autour du chef, avec `MapPathfinder` côté client.

**Spawn, étoiles, agression (P1.09).**
- **Composition.** `MonsterSpawner` (sim) compose les groupes à partir de `game/worlds/<id>/monsters.json` (les monstres de chaque sous-zone, `subareas.monsters`, avec leurs 5 grades ; boss et mini-boss exclus : `monsters.m_flags` bits 2 et 3). Chaque map a 2 à `max_groups` emplacements `{subarea}`, et un groupe vaincu réapparaît avec une nouvelle composition (1 à 4 monstres, grade au hasard : APPROX). Pas de groupe sans la capacité `ALLOW_MONSTER_RESPAWN` (`MapData.monster_spawn`, bit 13 de `mapsinformation.m_flags`, décodé comme les capacités de map de Dofus 2 : éteint sur les maps de zaap et dans la Taverne). Les mondes faits main gardent leurs groupes fixes (`groups` dans la map).
- **Étoiles.** `SubareaBonus` : bonus d'XP et de butin partagé par une sous-zone (Dofus 2.51), de −50 % à +100 %, aucun dans Incarnam et Astrub. Il monte avec l'horloge réelle (`Clock`) et baisse d'une étoile à chaque groupe vaincu (APPROX). Il est sauvegardé dans `Persistence` (`worlds`, `<monde>/stars`). Le combat le reçoit comme `rewardRate` (`Fight.reward_rate`, `luaformulas` 99), appliqué à l'XP et aux drops. Le groupe l'envoie dans `actor.bonus`, rafraîchi à chaque entrée sur la map.
- **Agression** (devblog 2.45, `MapInstance._watch`). Le chef voit à `aggressiveZoneSize` cases. Il attaque un personnage resté plus de 3 s dans cette zone si son niveau dépasse celui du personnage de plus de `aggressiveLevelDiff` (−200 : toujours), sauf immunité `aggressiveImmunityCriterion` (`CriteriaEval`) ou map sans `ALLOW_MONSTER_AGRESSION` (bit 20). En cas de choix, il attaque le premier vu, puis le plus faible. `group_alert{group, target}` prévient (le client affiche « ! »). Ensuite, `WorldFights.start_fight` fait comme un `fight_attack`.
- **Infobulle.** Membres (`name_id`, niveau, grade, XP de base), étoiles (textures `star0`/`star1`), XP estimée par `shared/FightXp.estimate`. Ce sont les mêmes formules `luaformulas` 2, 99 et 100 que `FightRewards`.

**Apparence des objets portés (P1.06b).** Le client Dofus 3 ne sait pas quel skin une coiffe, une cape ou un bouclier ajoute au look : c'est le serveur qui l'envoie. La source vient de l'émulateur JondoEmu (`equipment_skins.json`, lu par `tools/extractor/gamedata.py` → `items.json` `skin`, `skin_src`). Les valeurs y sont soit « measured » sur des captures, soit « inferred » par comparaison d'images ; les douteuses sont écartées.
- `LookBuilder.with_equipment(look, LookBuilder.worn_skins(worn))` ajoute les skins après le corps et le visage, dans l'ordre des emplacements. Le moteur de rendu masque les parties couvertes (`skinslotsrules`).
- `Character.display_look()` est le look montré : `player_stats.look`, l'acteur, le combattant, et la liste des personnages via `worn_look` sauvegardé. `Character.look` reste le look de création.
- `actor_look{id, looks}` prévient la map à chaque changement (`WorldItems.refresh_look`).

**Énergie, mort, fantôme (P1.10).** `sim/energy.gd` (`Energy`) et `Character.energy` / `life`. Les règles viennent du tutoriel du client Dofus 3 (`notifications` 12 à 14) :
- **Défaite.** Le personnage perd de l'énergie et revient au point de sauvegarde. À 0 énergie, il devient **fantôme** : `life` 2 = `GameRolePlayPlayerLifeStatus` phantom. Il n'y a plus de tombe dans Dofus 3 (déclencheur « 0:2 »).
- **Fantôme.** Il marche, mais il ne peut ni combattre, ni prendre un zaap, ni utiliser d'objet (`WorldSim.GHOST_FORBIDDEN`, APPROX). Les groupes ne l'agressent pas. Les autres joueurs le voient (`actor.life`).
- **Phénix.** `use_phoenix`, joueur à côté de `MapData.phoenix`, le ressuscite avec `Energy.PHOENIX` d'énergie. Les positions des phénix sont des données serveur : `links.json` `phoenixes`, APPROX. Elles vont dans `world.json` `phoenixes`, puis dans `player_stats.phoenixes` pour la carte du monde.
- **Récupération.** L'énergie revient avec les consommables (effet 139, `E_ENERGY_FULL` au maximum), et pendant la déconnexion (`saved_at` : 1 point par minute, 2 si la dernière map a `MapData.tavern`, bit 9 `ALLOW_TAVERN_REGEN`, `Character.rest_x2`). Un fantôme ne récupère rien.
- **Montants** (Dofus wiki) : 10 000 au maximum, 10 par niveau perdus à la défaite, 1 000 au phénix.
- **Messages.** Ce ne sont pas des erreurs : ils passent par `info{code, args}` (`Protocol.INFO_CODES`). Le client les affiche avec les vrais textes Dofus (`client/info_texts.gd` : clés i18n 5231, 4704, 4840, 5384 et la notification 14).

## Découpage de `WorldSim` et taille des fichiers (R.01)

`WorldSim` n'est qu'un **routeur** : connexion (`connect_player`, `disconnect_player`, sauvegarde), `tick`, `drain`, `handle` / `_handle` (validation, états qui bloquent une commande) et `_dispatch` (une commande vers le gestionnaire de son domaine), plus les cartes (`get_map`, `teleport`, `enter_map`). Les règles de chaque domaine sont dans des gestionnaires, des `RefCounted` sans `Node` qui héritent de `WorldHandler` (ils tiennent la sim dans `sim`) et que `WorldSim` expose en variables :

| Gestionnaire | Rôle |
|---|---|
| `items` (`WorldItems`) | gains d'objets (`give_item`), consommables, équipement, destruction, apparence portée |
| `travel` (`WorldTravel`) | déplacement, sortie de map, portes, zaaps, point de sauvegarde, `admin_cmd` (`/tp`) |
| `npcs` (`WorldNpcs`) | dialogues, boutiques, banque |
| `quests` (`WorldQuests`) | journal de quêtes : événements, récompenses, `quest_list` |
| `jobs` (`WorldJobs`) | récolte |
| `death` (`WorldDeath`) | fantôme, phénix, suites d'une défaite |
| `combat` (`WorldFights`) | début et fin des combats, combattants joueur et monstre, diffusion des événements |

L'API publique de `WorldSim` ne change pas (`give_item`, `save_point`, `zaap_destinations`, `teleport`, `get_map`, `handle`, `drain`…). Pour ajouter une commande : l'écrire dans le gestionnaire de son domaine, puis une ligne dans `WorldSim._dispatch`.

Côté combat et client, les plus grosses fonctions sont découpées de la même façon : `FightRules.zone` (une fonction par famille de formes), `FightEffects._apply` (`_apply_life`, `_apply_buff`, `_apply_removal`) et `FightDisplace` (poussées, téléportations, échanges), `FightView._apply_effects` (`_apply_effect`, `_effect_vitals`, `_effect_status`, `_effect_world`) avec `FightTexts` et `FightVisuals`, `ClientSession._dispatch` (`_on_actor_event`, `_on_npc_event`, `_on_quest_event`…). Dans `ClientSession`, l'action à faire une fois arrivé à côté de la cible (sortie, porte, zaap, phénix, PNJ, élément à récolter) est un seul objet `PendingAction` (au plus une à la fois, un nouveau clic la remplace) au lieu de variables `_pending_*`.

**Taille des fichiers** : `tests/test_architecture.gd` refuse un script de plus de 800 lignes (`src`, `addons`, `tests`, `tools`), sauf entrée dans `SIZE_EXCEPTIONS` avec sa raison (aucune aujourd'hui). On découpe par domaine avant la limite.

## Combat

Tout est dans `sim/fight/`, avec les formules officielles de Dofus 3 quand le client les contient (`luaformulas`). Le détail et les simplifications sont en tête de `fight_effects.gd` et `fight_rewards.gd`.

1. **Placement.** Un clic sur un groupe envoie `fight_attack{group}`. La sim retire le groupe et le joueur de la map, puis crée un `Fight` sur les mêmes cellules : les joueurs sur les cases rouges de la map, les monstres sur les bleues (à défaut, des cases libres autour de chacun). Elle envoie `fight_start{…, phase: "placement", placement, end}`. Ensuite, `fight_place{cell}` (échange avec un allié) et `fight_ready`, jusqu'à ce que tout le monde soit prêt ou que 30 s soient écoulées (`fight_begin{order}`).
2. **Tours.** L'ordre suit l'**initiative** ((100 + Force + Int + Chance + Agi) × PV/PVmax), en alternant les équipes. À chaque tour, les PA/PM repartent de leur maximum en tenant compte des buffs. Le tour dure 30 s. `fight_turn.effects` porte les effets du début de tour : buffs du joueur qui expirent, poisons.
3. **Actions**, validées par la sim (le client prévisualise avec les mêmes `FightRules`) :
   - `fight_move` : déplacement en 4 directions. Le **tacle** fait perdre des PM et des PA en quittant une case adjacente à un ennemi (part gardée = (fuite + 2) / (2 × (tacle + 2)), où tacle et fuite valent Agilité / 10). `fighter_move.lost` indique ce qui a été perdu.
   - `fight_cast` : vérifie les PA, la portée (+PO si le sort est modifiable), la ligne de vue, la ligne droite, la case libre ou occupée, les limites par tour et par cible, le délai de relance, la relance initiale et le **critère d'états** (`HS=498`, `FightRules.criterion_ok`). Le coup critique est tiré sur le RNG du combat.
4. **Effets** (`FightEffects`) :
   - dégâts (stat de l'élément + puissance, puis dommages fixes, puis résistances en %) ;
   - vol de vie, soins ;
   - poussée et attirance (dommages de collision), recul et avance ;
   - téléportation, échange, symétries ;
   - ±PA/PM (esquivables selon la sagesse) ;
   - buffs de caractéristiques, boucliers ;
   - **états**, et variantes conditionnelles (`cond` : état du lanceur ou de la cible, lu au moment du lancer : c'est la mécanique Sobre/Saoul du Pandawa) ;
   - poisons.

   Un buff décompte ses tours au début du tour de son lanceur (−1 = tout le combat). La mort d'un combattant dissipe les buffs qu'il a lancés.
5. **IA** (`FightAI.act`). Une action à la fois, uniquement via `fight.move()` et `fight.cast()`, comme un joueur, espacées pour laisser le client animer. Elle évalue chaque couple (case atteignable, sort, cible) : dégâts attendus sur les ennemis, alliés touchés en négatif, soins, retraits. Elle y va puis lance. Sinon, elle se rapproche de l'ennemi le plus proche. Elle est déterministe. **Profils (P1.16, `FightAI.profile`, APPROX : lus dans les sorts, la table `monsters` n'a pas de champ de comportement)** : agressif (corps à corps, se rapproche), prudent (sorts à distance seulement : garde sa portée), soigneur (soigne d'abord, va vers un allié blessé), invocateur (invoque d'abord), kamikaze (sort qui le tue : fonce). Le prudent, le soigneur et l'invocateur fuient sous 30 % de PV. Garde-fous (bug « un ennemi a arrêté de jouer ») : la fuite dure au plus `FLEE_MAX_TURNS` tours (APPROX(P1.16)), un fuyard acculé qui n'a rien pu faire combat, un monstre bloqué par un obstacle (aucune case atteignable plus proche à vol d'oiseau) contourne par le chemin réel (`_detour`), un tireur sans ligne de vue avance au lieu de rester à sa portée ; côté client, `SequenceGuard` / `FightView.watchdog` déclarent finie une séquence animée qui dépasse 15 s (sinon elle bloque tous les événements suivants).
6. **Fin et gains** (`FightRewards`, formules 99/100 du client) :
   - XP de groupe = Σ XP des monstres morts × coefficient de niveaux × bonus de groupe (÷ 4 en cas de défaite) × `rewardRate` (étoiles) ; formules partagées dans `shared/FightXp` ;
   - XP d'un joueur = cette XP de groupe × min(niveau, 2,5 × meilleur niveau monstre) / meilleur niveau joueur × (100 + Sagesse) / 100 ;
   - kamas (fourchette par monstre, partagée selon la prospection) et **drops** (`pct × prospection / 100`, un jet par joueur) pour les gagnants ;
   - `fight_end{result, duration, rewards}`, puis `map_enter` et `player_stats`.

   Victoire ou abandon : retour sur la cellule d'avant le combat. **Défaite** : retour au point de sauvegarde avec 1 PV, moins 10 × niveau d'énergie (P1.10 ; fantôme à 0). Le groupe vaincu réapparaît après 20 s, recomposé.

**Personnage.** `sim/character.gd` contient le niveau (table d'XP réelle), l'XP, les kamas, l'inventaire, le capital (+5 par niveau), les caractéristiques (P1.04 : coût par palier de `breeds.statsPointsFor*`, 1 capital par point jusqu'à 99 puis 2, 3, 4 dès 100 / 200 / 300, Vitalité 1, Sagesse 3 ; `reset_stats` rend le capital payé), les PV (50 + 5 × niveau + Vitalité, régénération 1 PV/s hors combat). Objets (P1.05) : `sim/Inventory` range des instances `{uid, id, qty, effects}` ; les uids viennent de `Persistence.next_uid("item")` (uniques dans tout le jeu) ; à la création (`WorldItems.give_item (WorldSim.give_item le relaie)` : drops…) les bonus de caractéristique (`effects.useDice` et `bonusType` ≠ 0) sont tirés une fois avec le RNG seedé du monde, les autres effets gardent leurs dés ; les objets identiques s'empilent. Au-delà des pods max (`StatFormulas.pods`), le personnage ne peut plus bouger (`overloaded`). `use_item` : soin (110), rappel au point de sauvegarde (600), parchemins (606-611, Force… additionnelle, avec `items.criterions`). Équipement (P1.06) : une instance portée a `pos` = son emplacement (`Equipment`, positions Dofus 0-15 via `itemtypes.superTypeId` → `itemsupertypes.possiblePositions`) ; `equip` vérifie le niveau (`items.level`), les conditions (`CriteriaEval`), un seul exemplaire de chaque Dofus. Les bonus des objets et des panoplies (`itemsets.effects[n − 1]`) s'ajoutent aux caractéristiques (`Character.stat`, donc au combattant). En combat, l'arme portée donne un sort propre au combattant (`Fighter.own_spells`, id `Equipment.WEAPON_SPELL`, construit depuis `items.apCost`, portée, critique et `criticalHitBonus`, zone `itemtypes.rawZone`) ; sans arme, « Coup de poing » (`spells` 0). Toutes les formules (PV, PA, PM, initiative, prospection, pods, tacle, fuite, esquive et retrait PA/PM) sont dans `shared/StatFormulas`, utilisé à la fois par le personnage (`player_stats.derived`) et par le combattant (avec ses buffs) et la dernière position. Il est sauvegardé par la `Persistence` injectée : en mémoire par défaut (tests), en fichiers pour le jeu (`FilePersistence`, `user://saves/characters/<monde>/<nom>.json`), en base de données plus tard côté serveur. Les sorts de classe (P1.03) : chaque classe a 22 paires de sorts (`spellvariants`), le personnage utilise un sort par paire (`variants`, commande `choose_variant`, hors combat) et chaque sort a jusqu'à 3 grades débloqués par niveau (`spelllevels.minPlayerLevel`) : `SpellBook.known_ids(breed, level, variants)`. Un sort lançable est un **grade** : id = 1 000 000 + `spelllevels.id` (comme les sorts de monstres). La barre de sorts (40 cases, `move_spell`, aussi en combat) est gardée sur le personnage ; un sort appris prend la première case libre et une variante prend la case de son sort jumeau (`SpellBook.bar_layout`). Un sort dont aucun effet n'est simulé est refusé (`spell_not_simulated`).

**Invocations (P1.11).** `sim/fight/Summons` : un effet `summon` (181, 1011, 1008 ; `double` 180 ; `replace` 405 / 2796) s'applique une fois, sur la cellule visée. Le monstre invoqué vient de `spells.json` `summons` (`spells.py summon_data` : grades, `bonusCharacteristics`, `monsters.m_flags` bit 0 emplacement d'invocation, bit 6 joue, bit 7 tacle). PV = PV du grade + bonus × (niveau de l'invocateur + 10) / 20, mesure de l'émulateur JondoEmu ; les autres bonus sont la part (%) de la même caractéristique de l'invocateur qu'elle reçoit à son arrivée (P1.11b, APPROX : 50 / 75 / 100 dans les données, dans l'élément de l'invocation). `monsters.characRatios` sert à la mise à l'échelle des monstres (luaformulas 3 / 4 / 5 / 12 via `characteristics.scaleFormulaId`), pas aux invocations. Limite : invocations à emplacement ≤ `StatFormulas.BASE_SUMMONS` + `summons` (caractéristique 26), sinon `summon_limit`. Une invocation qui joue passe juste après son invocateur (et ses invocations plus anciennes : `Fight.add_summon`), jouée par `FightAI` ; elle meurt avec lui (`Fight.handle_deaths`, en chaîne), ne retient pas son camp en combat (`_check_end`) et ne donne ni XP ni butin. Ids négatifs (-101, -102…). Effet `summon{summoner, fighter, order}` : le client ajoute le combattant (fondu) et reconstruit la timeline.

**Porter et lancer (P1.12).** `sim/fight/Carry` : effet `carry` (50, Karcham / Chamrak) : la cible voisine passe sur la cellule du lanceur, qui prend l'état 3 « Porteur » (`preventsSpellCast` : seuls les sorts qui l'exigent, critère `HS=3`, restent lançables : `Fighter.cast_forbidden`, `FightRules.needs_state`) et la cible l'état 8 « Porté » ; refusé sur un porteur, un porté, un stabilisé (`cant_be_moved`) ou un enraciné / alourdi (`cant_switch` = `spellstates.cantSwitchPosition`). Le porté suit son porteur (`Carry.follow` : marche, poussées, téléportations) et n'est plus sur le plateau (`Fight.fighter_at`, zones). Effet `throw` (51) : il atterrit sur la cellule visée, forcément libre, et Karcham / Chamrak portent `carry_range` cases plus loin (`FightRules.for_caster`, partagé par la sim, l'IA, le bot et l'aperçu du client). Les effets marqués `carried` (masque K) ne touchent que le porté du moment du lancer, les autres ne le touchent jamais. La mort du porteur ou du porté, ou un porté qui marche, sépare la paire (effet `drop`, aussi dans `fighter_move.effects`). Client : le porté devient une sous-entité du look du porteur (`LIFTED_ENTITY`, nœud `carried_3_0` de l'os), avec les vraies animations `AnimPickup`, `AnimThrow`, `AnimDrop` et `*Carrying` (`ActorView.carrying`).

**Pièges et glyphes (P1.13a).** `sim/fight/FightMarks` : `Fight.marks` (dicts `mark dict` du protocole). Un piège (400) se déclenche quand un combattant du bon camp entre dans une de ses cellules (`Fight.move` s'arrête dessus, poussées et téléportations aussi : `FightMarks.entered`) ; son sous-sort part du centre, lancé par le poseur, puis le piège disparaît. Glyphes 401 / 402 : leur sous-sort ne frappe que le combattant qui commence / finit son tour dedans (`FightEffects.apply_spell(..., only)`). Durée comptée sur les tours du poseur (`countdown`), marques retirées à sa mort, 2018 dissipe les marques d'un sort. Effets `mark_add` / `mark_remove` ; `fighter_move.triggered` porte ce qui se passe à l'arrivée ; les effets de fin de tour partent avec le `fight_turn` suivant. Le client colore les cellules (couleur réelle de la marque) et ne dessine pas les pièges de l'autre équipe.

**Déclencheurs, retardements, sous-sorts (P1.13b).** `sim/fight/FightTriggers` : un effet avec `on` (les `triggers` des données) pose un buff « trigger » sur sa cible pour `turns` tours ; il se déclenche sur ses codes : début / fin de tour (`Fight._next_turn` / `end_turn`), coup reçu (`FightEffects.damage` met le coup dans `Fight.hits`, `FightTriggers.flush` le traite après l'effet), soin (H), mort (X, dans `handle_deaths`). Les multiplicateurs 1163 / 1159 ne se déclenchent pas : ils multiplient les dommages subis et les soins reçus. Un effet avec `delay` devient un buff « delay » qui applique l'effet quand il expire (`FightEffects.expire`). `cast` lance un sous-sort sur la case de la cible (792 : c'est la cible qui le lance), sur 4 niveaux au plus. Une invocation lance son sort de départ en arrivant (`Summons`). Les glyphes-auras (`FightMarks.auras`) donnent les effets de leur sort à qui entre, et les reprennent à la sortie.

**Invisibilité et vue par équipe (P1.13c).** `sim/fight/FightVisibility.view(ev, fight, team)` donne ce qu'une équipe peut savoir d'un événement ; `WorldFights.fight_emit` l'applique à chaque joueur (le serveur fera de même par connexion). Un invisible (état au drapeau `invisible`) de l'autre équipe marche sans chemin, a `cell` -1, lance ses sorts avec `from` ; les pièges de l'autre équipe ne sont pas envoyés. La fin de l'invisibilité envoie `reveal {cell}` à tous. L'IA ne voit que ce que voit son équipe.

**Runes et bombes (P1.13d).** Une rune (`FightMarks`, kind `rune`) ne part que par l'effet 2023 qui atteint un combattant posé dessus : son lanceur lance le sort de la rune sur sa case. Une bombe est une invocation dont le monstre a `explode` / `chain` / `instant` / `wall` dans `spells.json` `summons` (tables `spellbombs`, `spellbombwalls`) : 1009 → `Summons.detonate` (réaction en chaîne, puis explosion qui tue la bombe ; `Fighter.exploded` laisse finir le sort d'un lanceur mort). Les murs sont des marques recalculées avec les auras (`FightMarks.walls`). Les conditions d'un sort (états du lanceur et des cibles, monstres `F` / `f`, `p` / `P`) sont lues telles qu'au lancer.

**Portails (P1.13f).** Un portail (`FightMarks`, kind `portal`, effet 1181) est une marque d'une case. Les portails actifs d'un lanceur forment un réseau dès qu'il y en a deux : un combattant dont la marche s'arrête dessus, ou touché par 1182 (Exil), passe de portail en portail (le plus proche non visité) et sort par le dernier (`FightMarks.cross`, déclencheurs PT / CPT). Un sort lancé sur un de ses portails est projeté : `Fight.cast` le fait atterrir sur la sortie, `Fighter.projecting` porte le bonus (+#3 % et +#1 % par case) et répond aux masques `R` / `r`, `Fight.cast_from` donne l'origine des zones et poussées. 1183 désactive des portails jusqu'au tour de celui qui les a coupés.

**Formes et redirections (P1.13e).** Les lettres de zone sont nommées par l'enum du client `SpellZoneShape` (`docs/client_enums.md`) et dessinées par `FightRules.zone` (dont `l` ligne depuis le lanceur, `V` cône, `U` demi-cercle, `F` fourche, diagonales). Trois effets à déclencheur agissent sur le coup lui-même dans `FightEffects.damage`, qui renvoie tous les coups : 765 (l'intercepteur le prend), 1061 (réparti entre les porteurs du même partage) ; 786 part après le coup et soigne l'attaquant (`Fight.trigger_from` / `trigger_amount`). 1165 est un glyphe (`glyph_now`) qui lance son sort tout de suite sur qui s'y trouve. `CCMPARR` part une fois par PM utilisé en marchant.

**Formes lues dans le code du client (P1.13g).** `FightRules.zone` suit les classes natives `SpellZoneShape*Behavior` (fabrique `gru.blgy`, lue avec `tools/client_code`) : `param2` est un minimum pour les cercles, croix et lignes (`C2` avec `param2` 1 n'a pas de centre), les bras diagonaux comptent leurs pas (une case en diagonale = les deux coordonnées), le carré fait au moins 3 × 3, `W` n'a pas de centre, la fourche a des dents de `param1 + 1` cases, `l` ne s'arrête sur la cible que si `isStopAtTarget`. Nouvelles formes : `D` damier, `B` boomerang, `R` rectangle, `Z` hors du cercle euclidien. La direction d'une zone est celle du lanceur vers le centre si ils sont alignés (ligne droite ou diagonale : `FightRules.dir8`), sinon aucune : une ligne ou un cône ne touche alors que la case ciblée. `N` et `;` n'ont pas de géométrie dans le client (point).

**Baisse des dommages en zone (P1.13j).** Une zone porte `step` / `steps` (`zoneDescr.damageDecreaseStepPercent` / `maxDamageDecreaseApplyCount`, ou la fin de `itemtypes.rawZone` pour une arme). `FightRules.efficiency(zone, centre, origine, case)` donne le pourcentage perdu sur une case, comme les classes natives de `gru.blgz` : min(100, min(distance − décalage, `steps`) × `step`), la distance dépendant de la forme. `FightEffects.apply_spell` le calcule par cible pour les dommages, vols et soins directs (`ZONE_DECREASE`, champ `zone_pct` de l'effet) ; `damage` / `heal` l'appliquent après les bonus du lanceur, avant les résistances de la cible.

**Options de zone (P1.13l).** `spells.py zone_of` ajoute `sight` (`zoneDescr.onlyAffectIfInSightLine`), `with_carried` (`includeCarried`, écrit seulement hors des points : tous les points l'ont) et la forme `custom` (`;`, `cells` = `cellIds` absolues). `FightRules.zone_in(map, occupés, zone, centre, origine)` = `zone` moins les cases hors de vue du **centre** (code natif `gtb.blnw`) ; `FightRules.area(sort, centre, origine, map, occupés)` en fait autant pour l'aperçu du client. `FightRules.touches_carried` : un porté (état 8) n'est touché par une zone qu'avec `includeCarried` (`gtz.nhs`) ; `FightEffects.targets` le cherche sur la case de son porteur. Un sort en point sur un porteur touche donc aussi le porté. `forcedDirection` n'a pas de lecteur dans le client (serveur seul).

**Masques de cible lus dans le code du client (P1.13h).** Chaque effet garde son `targetMask` brut (`mask`, `tools/extractor/spells.py`) ; `sim/fight/target_mask.gd` (`TargetMask`) le vérifie cible par cible comme la classe native `gtz` : un masque vide touche tout le monde, sinon il faut une lettre de camp (`a` / `g` alliés, `a` et `C` / `c` seuls à toucher le lanceur, `C` même hors de la zone, `A` ennemis, `h` / `l` personnages, `m` monstres, `j` invocations, `i` / `s` invocations non statiques / statiques, minuscule = alliés, majuscule = ennemis) et que toutes les conditions tiennent (`E` / `e` états, `F` / `f` monstres, `B` / `b` classes, `V` / `v` % de vie, `R` / `r` projeté, `P` / `p` famille d'invocation du lanceur, `K` porté par le lanceur ou lancé par lui pendant ce lancer, `W` déplacé pendant ce lancer, `T` téléfragué pendant ce lancer (P1.13n), `U` invoqué pendant ce lancer, `O` / `o` auteur du coup déclencheur, `Q` / `q` limite d'invocations, `PB` / `pb` bouclier ; plusieurs `B` / `F` / `Z` = au choix). « Pendant ce lancer » se lit dans `Fight.cast_log` (P1.13k), la liste d'événements par combattant de l'aperçu du client (`FightState.bmjp`) : le `FightEffects.apply_spell` le plus externe la vide, ses sous-sorts la partagent ; les déplacements par effet, les lancers (`Carry.throw`), les portails et les invocations y écrivent (`Fight.log_cast`). Statique = `monsters.canPlay` faux (`gyn.bmqg`). `target` (enemies / allies / all / caster) n'est plus qu'un résumé pour l'IA, les marques et les infobulles.

**Codes de déclencheurs lus dans le code du client (P1.13i).** L'aperçu de combat du client (classe native `gzp`) dit quel événement allume quel code (bits de `Core.Features.Fight.Spells.Triggers`, analyseur `grr.blfl` : les lettres de chaque partie « | », un code inconnu est ignoré ; `EON<n>` / `EOFF<n>` gardent leur état, `EK:<masque>` son masque). `FightTriggers` : coup subi (`D`, élément, `DBA` / `DBE`, `DM` / `DR`, `DS` sort non déclenché, `DT` / `DG` piège / glyphe, une poussée contre un obstacle = `PD` seulement), ce que fait le porteur (`CD…`, `CH` soigne, `CS` bouclier, `CC` coup critique, `K` achève, `EK:<masque>` une mort que le masque accepte), déplacements (`M`, `P` poussé, `MA` attiré), `APA` / `MPA` / `R` / `LPU` (PA, PM, portée en baisse, vitalité en hausse), états (`EON<n>` / `EOFF<n>`, `ION` / `IOFF`). Les coups et les événements attendent dans `Fight.hits` (`FightTriggers.event`) jusqu'au `flush` ; `Fight.hit_source` dit d'où vient un coup, `Fighter.last_hit_by` qui l'a frappé en dernier. P1.13m ajoute `MS` (échangé), `PO` (le porteur déplace un combattant), `CAPA` / `CMPA` (il vole des PA / PM : effets 84 / 77, `resource` `steal`), `DIS` (désenvoûté : effet 132, qui retire les buffs de `dispellable` 1 ; `Buff.dispellable`, les écouteurs `DIS` sont lus avant le retrait), `DCAC` / `CDCAC` / `KWW` (arme : `Fight.cast_weapon`), `DCCBA` / `DCCBE` / `CDCCBA` / `CDCCBE` (coup critique : `Fight.cast_crit`), `CION` / `CIOFF`, `V` / `VA` (toute sortie de vie : coup, poussée, soin, bouclier ; `VM` / `VE` = érosion, jamais ici) et `PPD` ; `M` n'est pas filtré par genre (le client vérifie seulement la case d'arrivée). Les codes que le client ne connaît pas (`XD`, `XPD`, `XDM`, `XDTB`, `CPD`) ou que son aperçu n'allume jamais (`CI`, `CT`, `TP`, `DTB`, `DTE`, `DV`, `CMPARR`, `CAPAS` / `CMPAS`…), et `DI`, `PMD`, `PST` / `PDT`, laissent le sort `partial`.

**Téléfrag (P1.13n).** Lu dans l'aperçu des téléportations du client (`hai.bnca` / `dht` / `hbl` / `mwk`, `gvr.st`, `gvr.bmdf`) : une téléportation (`teleport` 4, symétries 1104 / 1105, échange 8 / 1101 : l'effet garde son id, `effect`) vers une case occupée **échange** les deux combattants, si c'est permis dans les deux sens (`FightEffects.can_swap`) : aucun des deux ne porte (état 3), celui qu'on teste n'est pas porté (état 8), ni stabilisé (`cantBeMoved`, propriété d'état 3), ni enraciné pour les effets de `gzj.bmxr` (`cantSwitchPosition`, propriété 18 : 8, 784, 1099, 1100, 1104-1106 ; pas 4 ni 1101), et un monstre a besoin de `monsters.canSwitchPos` (`canSwitchPosOnTarget` s'il est le lanceur ; `m_flags` bits 9 / 10) sauf pour 4 et 1023 (`gzj.bmww`). Sinon rien ne bouge. Le déplacement de l'occupant vient d'abord ; les deux portent `swapped` et `telefrag`. Téléfrag = le lanceur est un Xélor (`breedId` 5, lu à `gyn` +0x14) ; il est noté dans `Fight.cast_log` et `T` le lit : les sorts Xélor lancent alors leur sous-sort Téléfrag (états 251 ennemi / 244 allié, 2 tours) et leurs bonus « sur Téléfrag ». L'aide du jeu le dit (i18n, « Les Téléfrags ») : « générés lorsque deux entités échangent de positions suite aux effets de téléportation d'un sort Xélor ». **Retours en arrière (P1.13q).** `Fighter` garde `prev_cell` (avant son dernier déplacement, par le setter de `cell`), `turn_begin_cell` (début de son tour) et `start_cell` (début du combat) ; 1100 « Téléporte à la position précédente » (`rollback_prev`), 1099 « … de début de tour » (`rollback_turn`), 784 « … de début de combat » (`to_start`) y envoient la cible, 1106 « Téléportation symétrique » (`sym_impact`) la renvoie de l'autre côté du point d'impact, 1023 (échange forcé) est un `swap` sans `gvr.st`. Une case d'arrivée occupée échange comme toute téléportation (Téléfrag pour un Xélor). APPROX(P1.13q) : le point de symétrie de 1106 n'est pas lu dans le client (la case visée).

**Non simulé (prochaine vague)** : codes de déclencheurs que le client ne connaît pas ou que son aperçu n'allume jamais (P1.13m), renvoi de sort (106 / 107 / 220, sorts de monstres seulement), Téléfrag des retours en arrière (1099 / 1100 « position précédente / de début de tour », non extraits), érosion, sons (rejoindre un combat et les spectateurs : côté sim en P3.04a, client en P3.04b).

**Challenges, fuite, options, timer (P1.15)** : `sim/fight/fight_challenges.gd` tire 1 à 2 challenges au début du combat (table `challenges`, règle écrite à la main par challenge, `APPROX(P1.15)` pour le bonus 25 % d'XP et de drop par challenge réussi, `FightRewards`), `challenge_list` / `challenge_update`. `fight_option` (chef seulement : locked, party_only, secret, help) -> `fight_options`. `fight_leave` : fuite au placement, abandon en combat (compte comme mort pour les challenges ; seul, le combat est perdu). Le tour finit seul à 30 s. Client : bandeau des challenges, boutons d'option, chrono dans `FightHud`.

**Rejoindre et regarder un combat (P3.04a).** Un combat est un acteur de sa map (`FightActor`, `kind: fight`, les épées : équipes, phase, options), créé par `WorldFightWatch` au début et renvoyé par `actor_add` quand ces valeurs changent. `fight_join{fight, team}` (placement seulement, équipe des joueurs, 8 par équipe, options `locked` / `party_only`) fait entrer le joueur comme combattant (`fight_start` chez lui, `fighter_joined` chez les autres) ; `fight_spectate{fight}` le met hors de la map avec `fight_watch` (l'état du combat) puis tous les événements, sans pouvoir agir (`spectating`). Un joueur qui fuit ou se déconnecte alors que d'autres restent quitte seul (`Fighter.left`, pas de gain). Messages dans `shared/protocol_watch.gd`. Voir `tests/test_fight_join.gd`.

**Combats à plusieurs, côté client (P3.04b).** `ClientSession` crée une `FightSwords` pour tout acteur `kind: fight` (clic : menu « Rejoindre » / « Regarder » selon `phase` et `options`) ; `FightFlow` (`client/fight_flow.gd`) gère la vie de la `FightView` : `fight_start` (combattant, aussi après avoir rejoint), `fight_watch` (spectateur : `FightView.spectator`, `you = -1`, pas de barre de sorts, bouton « Quitter »), `fighter_joined` / `fighter_left`, `fight_end` (fenêtre de gains seulement pour un combattant qui va au bout). Voir `tests/test_fight_watch_client.gd`.

**Séquenceur client.** Le client applique les événements dans l'ordre (`ClientSession._pump`). Un `spell_cast` ou un `fighter_move` lance une séquence visuelle dans `FightView`, et les événements suivants attendent sa fin (signal `sequence_done`), comme dans le client Dofus. Une séquence de sort se déroule ainsi :
1. l'animation du lanceur jusqu'à son label `SHOT` ;
2. le FX (os de FX Dofus du script du sort, sinon `SpellFx` procédural) ;
3. les effets : chiffres colorés par élément, PA/PM, états et buffs, glissade des poussées, `AnimHit` / `AnimMort`, et mise à jour des PV.

À la fin, `FightResultWindow` affiche les gains (XP et barre de niveau, kamas, objets avec leurs icônes). Le HUD d'exploration (`PlayerHud`) montre le niveau, l'XP, les PV et les kamas ; la touche I ouvre les caractéristiques et l'inventaire.

Les PV ne sont appliqués qu'à l'impact, et une victoire n'interrompt jamais le dernier coup.

## PNJ et dialogues (P2.01)

Les PNJ sont des `NpcActor` placés par `worlds/<id>/npcs.json` (`gamedata.py npcs <monde>`, positions réelles du serveur Ankama via JondoEmu) avec leur modèle de la table `npcs` (nom, look, actions). `Dialog` (`sim/`) lit un arbre `{start, nodes}` : les réponses dont le `criteria` échoue (`CriteriaEval`) ne sont jamais envoyées ; une réponse peut avoir une `action` (`teleport`, `give_kamas`, `give_item` exécutées par la sim ; `shop`, `quest` transmises). Sans arbre écrit à la main (clé `dialogs` de `npcs.json`), un PNJ dit son premier message (APPROX : l'arbre est côté serveur). Le joueur doit être sur une case voisine ; toute autre commande ferme le dialogue. Le client (`DialogWindow`) affiche les textes i18n par `text_id`.

**Boutiques de PNJ (P2.02).** `worlds/<id>/shops.json` : `{shops: {npc id: {items: [items.id]}}}` (`gamedata.py shops <monde>` : contenus réels du serveur, JondoEmu `npc_shops.json`, 51 marchands dans `dofus` ; Incarnam n'a aucun vrai marchand, `shops.json` y est écrit à la main, APPROX). Un PNJ qui a une boutique reçoit le bouton « Acheter/Vendre » (i18n 8944) dans son dialogue (`Dialog.with_shop`), ou ouvre sa boutique directement s'il n'a rien à dire ; l'action `shop` d'un dialogue écrit à la main l'ouvre aussi. `shop_open{npc, items:[{item, price}], sell_divisor}` ; `shop_buy{item, qty}` et `shop_sell{uid, qty}` (joueur à côté du PNJ, un fantôme ne commerce pas, toute autre commande ferme la boutique : `shop_end`). Règles dans `shared/NpcShop` : achat au `items.price`, rachat à `price / 10`, refus faute de kamas (`not_enough_kamas`), si les pods dépasseraient le maximum (`overloaded`), objet non vendu (`no_shop`), objet à prix 0 non racheté (`not_sellable`), objet porté (`item_worn`). Client : `ShopWindow` (onglets Acheter / Vendre, quantité commune, boutons grisés par `NpcShop`).


**Banque (P2.08).** Un coffre par compte (`sim/Bank` : kamas + piles d'objets, un `Inventory`), rangé dans le document de compte de `Persistence` (`accounts/<compte>`, clé `bank` ; un compte vide partage le coffre `_local`) : tous les personnages du compte, dans tous les mondes qui partagent le magasin, voient le même coffre. Il est relu à chaque opération et écrit avec le personnage par `Persistence.commit` (un objet n'est jamais dans les deux endroits ni dans aucun ; en serveur : une transaction). Un PNJ est banquier s'il est dans `worlds/<id>/bank.json` (`bankers`, `placed` pour ceux que les données réelles ne posent pas dans ce monde, APPROX) ; son dialogue reçoit « Consulter son coffre personnel. » (i18n 913010, la réplique du banquier 6394 : `Dialog.with_bank`, action `bank`), ou le coffre s'ouvre directement s'il est muet. `bank_open{npc, cost, kamas, items}` (l'accès est payé à l'ouverture, `not_enough_kamas` sinon), `bank_move{uid, qty, dir}` (`in` : pile du sac, `out` : pile du coffre, effets conservés, sans nouveau tirage) et `bank_kamas{amount, dir}`, réponses `item_added` / `item_removed` + `player_stats` + `bank_update{kamas, items}` (`qty` 0 = pile disparue), `bank_close` / `bank_end` (même règle de distance et de fermeture que les boutiques ; `no_bank` sans coffre ouvert). Règles dans `shared/BankRules` : le texte du banquier (i18n 913012) donne un coffre unique par compte, payant à chaque accès, au prix qui dépend du nombre d'objets entreposés ; APPROX(P2.08) : 1 kama par pile, aucune formule dans le client. Retrait refusé au-delà des pods (`overloaded`), objet porté refusé (`item_worn`). Client : `BankWindow` (deux grilles Sac / Coffre, double-clic = déplacer la quantité de la boîte, ligne de kamas déposer / retirer).

## Quêtes (P2.03)

`worlds/<id>/quests.json` (`gamedata.py quests <monde>`, tables Dofus 3 `quests` / `queststeps` / `questobjectives` / `queststeprewards`) : `{quests: {id: {name_id, criteria, start: {npc, map}, steps: [{objectives: [{id, type, map, params, args}], rewards: [lignes par niveau]}]}}}`. `WorldSource.get_quests()` les donne à la sim. L'état d'un personnage est un `QuestLog` (`Character.quests`, sauvegardé avec lui : quêtes en cours avec l'étape et le compteur de chaque objectif, quêtes finies) ; les règles sont des fonctions pures de `QuestEngine`, sans état ni `Node`, donc identiques en standalone et sur serveur :

- `offers` / `with_offers` : un PNJ propose les quêtes dont il est le départ (`start.npc`), non commencées ni finies, dont le `criteria` passe (`CriteriaEval` : `BT`, `Qf`, `Qa`). L'offre est une réponse ajoutée au dialogue du PNJ pour ce joueur (`PlayerActor.dialog_tree`, id de réponse = `REPLY_BASE` + id de la quête, action `quest_start`) : le client n'envoie rien de nouveau, c'est un `dialog_reply`.
- `on_event` : `WorldSim` rapporte ce qui arrive (`talk` avec un PNJ, `map` atteinte, `fight` fini avec les ids des monstres, `use` d'un objet, `item` quand le sac change) ; le moteur fait avancer les objectifs de la série en cours (voir `active_run` : les objectifs consécutifs de même type se font dans n'importe quel ordre, la série suivante s'ouvre ensuite) et rend des changements (`start`, `update`, `step`, `finish`, objets remis). `WorldQuests.apply_changes` les applique : objets de la remise (type 3) retirés du sac, récompenses de l'étape finie (`QuestEngine.rewards` : ligne du niveau, XP, kamas, objets, émotes / titres / sorts gardés dans le personnage), messages `quest_start`, `quest_update` (vue complète, `rewards` si une étape vient de finir), `quest_complete`, puis `player_stats`. `quest_list` arrive à la connexion.
- Types d'objectifs suivis : 0 (texte, sur une map), 1 aller voir, 2 montrer un objet, 3 ramener des objets, 4-5 découvrir une map / une zone, 6 / 16 vaincre N monstres en un combat, 7 vaincre, 8 utiliser un objet, 9 retourner voir, 14 vaincre N monstres, 17 fabriquer (APPROX : l'objet dans le sac). Les autres (escorte, défi, âmes, Krosmaster) : P2.03b.

Client : `QuestWindow` (journal, Q) garde la copie des quêtes du joueur, `QuestTracker` (sous la minimap) la lit ; les phrases viennent des textes du client (`questobjectivetypes.nameId` + `args`, `QuestTexts`). Rien de la règle n'est dans le client.

P2.04a : `QuestEngine.can_start` (quête non en cours ; déjà faite = seulement si `repeat` 1, ou 2 / 3 et un jour réel de plus, `QuestLog.finished_day`) ; les chaînes sont des critères `Qf=`. `quest_abandon{quest}` retire la quête et renvoie `quest_list`. `map_markers` (offres des PNJ de la map, objectifs actifs de la map) est calculé par `WorldQuests.send_markers`, jamais par le client.

## Métiers : la récolte (P2.05)

`worlds/<id>/interactives.json` (`gamedata.py interactives <monde>`) : `{maps: {id de map: [{e, cell, gfx, skill}]}}`, les éléments récoltables ; `WorldSource.get_map` les met dans `MapData.interactives` (envoyé au client dans `map_enter`). Les tables `skills` et `jobs` sont des copies légères dans `game/data/tables`.

- `shared/Jobs` : les règles pures (niveau requis `skills.levelMin`, quantité, XP, niveaux). Tout ce que le client ne donne pas est `APPROX(P2.05)` dans ce fichier.
- `sim/JobLog` : l'XP de chaque métier, dans `Character` (sauvé, `player_stats.jobs`). `sim/InteractiveState` : l'état des éléments d'une map (repousse, élément pris), un par `MapInstance`, donc partagé par ses joueurs.
- `interactive_use{element, skill}` (`WorldJobs.on_interactive_use`) : joueur à côté, niveau suffisant, élément libre. La map reçoit `interactive_start` (animation) ; à la fin (`_tick_harvest`) : `give_item`, `job_xp`, `interactive_state{ready: false, until}` ; plus tard `ready: true`. Tout autre déplacement ou commande, un combat ou la déconnexion annulent (`interactive_end{done: false}`).
- Client : un clic sur une ressource (`MapData.interactive_near`) marche à côté puis envoie `interactive_use` (comme une porte) ; il ne contient aucune règle.

## Forgemagie (P2.07a)
- `shared/Smithmagic` : règles pures (runes = objets de type 78, poids par unité, chance, issues `crit` / `success` / `neutral` / `fail` / `overmax`, puits, `preview` pour la fenêtre). Le client ne contient aucune formule de forgemagie : tout est `APPROX(P2.07)` (voir le lot dans `ROADMAP.md`).
- `sim/WorldSmithmagic` : `fm_apply{uid, rune}` sur un équipement du sac (pas porté) -> la rune est consommée seulement si elle agit, une pile donne un objet, `fm_result{outcome, item, lost}` + `item_added` / `item_removed`. Dés : le `rng` de la sim (déterministe par graine). Erreurs : `fm_item`, `fm_rune`, `fm_reserve`.

## Métiers : le craft (P2.06a)

`recipes` (copie légère, `gamedata.py table recipes --fields resultId,resultLevel,ingredientIds,quantities,jobId,skillId`) : une ligne par objet fabriqué ; une compétence qui apparaît dans `recipes.skillId` est une compétence de craft (Forger, Coudre...).

- `shared/Crafting` : l'index des recettes (par compétence et par ensemble d'ingrédients), les cases selon le niveau, le grimoire (`book`), l'XP. `APPROX(P2.06)` dans ce fichier : cases = 2 + niveau/20 (max 8), XP = 10 + niveau de l'objet par fabrication.

Erreurs : `no_craft`, `no_recipe`, `craft_slots`, `missing_ingredients`.
- Client (P2.06b) : `CraftModel` (état sans Node : suit `craft_state`, construit `craft_set` / `craft_do`) et `CraftWindow` (touche J : sac, cases, résultat, Fabriquer, grimoire ; liste des compétences `Crafting.craft_skills()`). Fermer envoie `craft_close`.
- Aucun élément d'atelier sur les maps (donnée serveur absente) : l'atelier s'ouvre n'importe où (APPROX). Fenêtre cliente : P2.06b.

## Contenu d'un monde : `ContentSource` (C.01)

Tout ce que le jeu lit dans `content/`, `data/`, `worlds/<id>/` et `mods/` passe par `shared/content_source.gd`, avec des **chemins logiques** (`data/spells.json`, `worlds/dofus/npcs.json`, `content/Content/Data/breedsdataroot.json`). Deux racines : `res://` (dev et solo, par defaut) ou le cache `user://worlds/<id>/` telecharge d'un serveur (marque par `manifest.json` ; il contient `content/`, `data/`, `mods/` et `world/` = la definition du monde actif). `ContentSource.use_world(id)` choisit le monde ; sans cache, repli sur `res://`. Un cache pret repond seul.

- `DataFiles` (sim et shared), `GameData`, `SpellBook`, `Mods`, `JsonWorldSource.for_world` : chemins logiques via `DataFiles` / `ContentSource` ; le serveur et le client lisent donc les memes octets.
- Le rendu : `addons/dofus_renderer` ne connait que son interface `DofusContentProvider` ; le reglage `dofus_renderer/content_provider_script` (project.godot) y injecte `client/content_provider.gd` (`ContentSourceProvider`, mods puis `content/`).
- Verifie par `test_architecture` : aucun `res://content|data|worlds|mods` en dur hors de la couche (liste blanche justifiee) ; `FileAccess` / `DirAccess` interdits dans `shared/` et `sim/` sauf `content_source.gd`.
- Les tests (`test_content_source.gd`) comparent les octets lus depuis `res://` et depuis un cache de test.

## Paquets de monde et API de contenu (C.02)

Le serveur construit pour chaque monde un **paquet** (`server/world_package.gd`) : `manifest.json` = `{format: 1, world, name, module, version, files: [{path, hash, size}]}` (`shared/content_manifest.gd`, pur). `path` est logique, `hash` = SHA-256, `version` = hash des lignes `chemin:hash` triées. Contenu : `worlds/<id>/**`, `data/**` et les globs de `world.json` `content`. Rien n'est copié : `<package-dir>/<id>/` ne garde que `manifest.json` et `index.json` (cache date/taille/hash) ; les octets sont servis sur place, par hash.

Second port HTTP (`--http-port`, `ServerHost.listen_http`) : `GET /worlds`, `/worlds/<id>/manifest.json`, `/worlds/<id>/files/<hash>` (`Content-Length`, `ETag`, `Range`). `Authorization: Bearer <jeton de login_ok>` obligatoire (401 sinon) ; seul un hash du manifeste est servi (le client ne fournit jamais de chemin) ; un serveur sans comptes ne sert rien. Côté client, `client/content_client.gd` (sans écran) compare le manifeste au cache, télécharge ce qui manque (`.part` repris par `Range`, SHA-256 vérifié, renommage atomique), supprime le périmé et écrit `manifest.json` en dernier, ce qui rend le cache lisible par `ContentSource`.

### Zip de base d'un monde (C.05)

Une première installation fichier par fichier coûte une requête par fichier (Incarnam : 19 880). Le serveur construit donc aussi un **zip de base** par monde (`server/world_bundle.gd`) : un exemplaire de chaque contenu distinct, entrée nommée par son SHA-256, en parties `part-NNN.zip` (~256 Mo de fichiers, `--bundle-mb`, `--no-bundle`) ; webp, png, ogg… sont stockés, le reste compressé. Le découpage est calculé à partir du manifeste (`shared/content_bundle.gd`, pur) : l'index `GET /worlds/<id>/bundle.json` ne porte que la taille et l'empreinte de chaque zip, `GET /worlds/<id>/bundle/<part>` sert un zip (jeton, `Range`, liste blanche = noms de l'index). Le client (`ContentClient.install_bundle`, appelé par `WorldLoader.install`) ne prend le zip que pour les parties qui pèsent moins de 90 % des fichiers manquants qu'elles contiennent (première installation oui, mise à jour d'un fichier non) : téléchargement repris par `Range` dans `<monde>/_bundle/`, empreinte du zip comparée à l'index (un zip abîmé est refusé), décompression `ZIPReader` avec vérification de chaque fichier contre le manifeste, zip supprimé ; un zip inutilisable retombe sur le téléchargement fichier par fichier. `ContentClient.download` termine toujours la mise à jour (fichiers périmés, `manifest.json`).

### Sélection des assets d'un monde (C.02b)

`game/content/` pèse 22 Go : un paquet n'en prend que ce que le monde utilise. `server/world_assets.gd` (`WorldAssets`, pur : lectures de fichiers sous une racine, aucun état du jeu, testable sur un monde minuscule) calcule la liste de globs, lancé par `godot --headless --path game -s res://tools/world_assets.gd -- --world=<id>` l'écrit dans `worlds/<id>/_content.json` (`{stats, bytes, globs}` ; le `_` le garde hors du manifeste, `WorldPackage` le lit en plus de `world.json` `content`, et `build_release.py` le copie pour le serveur). Sources : les maps du monde (`Content/Maps/<id>.json`, textures `Maps/Gfx/<g>` de leurs calques, props animés `Animations/Props/<g>/*`) ; les looks des monstres (`monsters.json`), PNJ (`npcs.json` + table `npcs`), invocations (`spells.json` `summons`), de chaque corps et visage jouables (`breeds`, `bodies`, `heads` à la création) et des objets que le monde distribue (butins, boutiques, récompenses de quêtes, recettes : `items.json` `skin`) : dossiers d'os (tous les paquets d'une famille d'os comme celui du joueur) et de skins, sous-entités comprises ; et le socle commun (`Fonts`, `UI`, `I18n`, `Worldmaps`, `Picto/{Spells,Items,Monsters}`, tables brutes `bodies`, `breeds`, `skinslotsrules`). Un dossier = un glob `dir/*`, un fichier de map ou de texture = son chemin littéral (la construction ne parcourt jamais les 62 000 fichiers de `Maps/Gfx`). Incarnam : 1,9 Go au lieu de 22 Go.

Vérifier la couverture : `ContentSource.trace_start()` / `trace_stop()` enregistre les chemins logiques lus ; `client_shot --trace=<fichier>` en écrit la liste d'une session, `tools/world_assets.gd --check-trace=<fichier>` liste ce que le paquet ne contient pas (code 1 s'il en manque). APPROX(C.02b) : un objet que le monde ne distribue jamais n'a pas de skin dans le paquet.

### Zones d'un grand monde (C.02c)

Un monde de 17 000 maps ne se télécharge pas d'un bloc. `world.json` peut déclarer `zone_key` (le champ des fichiers `worlds/<id>/maps/<map>.json` qui range les maps : `subarea`) et `server_only` (globs de chemins que le serveur lit et que le client ne lit jamais : `worlds/dofus/maps/*`, les 17 353 fichiers de la sim). `tools/world_assets.gd --world=<id> --zones` (`WorldAssets.compute_zoned`) écrit alors dans `_content.json` : `globs` = la **base** (interface, polices, personnages jouables, boutiques et quêtes, et la zone de `start_map`) et `zones` = pour chaque zone `{maps, files: {dossier: [noms]}, dirs: [globs], bytes}` (maps, textures, accessoires animés, monstres de la sous-zone via `monsters.json`, PNJ de ses maps). Un fichier que deux zones utilisent est listé dans les deux (le client le télécharge une fois).

`WorldPackage` construit le manifeste de base comme avant, plus un manifeste par zone (`Built.zones` : un manifeste ordinaire + `zone`) et l'index `ContentZones` (`Built.zone_index` : `{version, start_zone, zones: {id: {version, files, size, maps}}}`). Routes : `GET /worlds/<id>/zones.json` (404 si le monde n'est pas découpé), `GET /worlds/<id>/zones/<zone>/manifest.json` ; les octets passent par `/files/<hash>` (liste blanche inchangée). `GET /worlds` ajoute `zones` et `zones_size`. Le zip de base (C.05) ne contient que la base.

Côté client, `ContentClient.fetch_zones / fetch_zone / install_zone` (reprise par `.part`, hash vérifié, manifeste de la zone mémorisé dans `_zones/<zone>.json` une fois complète) et `ZoneStreamer` (sans écran : `load_index`, `ensure(map)`, `prefetch(voisines)`, `zones_to_fetch`, rappel `on_zone` pour l'indicateur). Les fichiers déjà au cache (partagés avec une autre zone) ne sont pas redemandés ; un monde sans zones répond « rien à faire ». Branchement (C.02d) : `ZoneGate` (nœud du client, créé par `LaunchScreen` pour un monde de serveur) retient chaque `map_enter` dont la zone n'est pas au cache (`admit`, appelé par `SessionLink`), la télécharge dans un fil (`ZoneStreamer.ensure_zone`), affiche `ZoneIndicator` (barre, ou message d'erreur puis nouvel essai), puis rejoue l'événement (`zone_ready`) ; une fois la map montrée, les zones des maps voisines sont préchargées derrière. Sans index (monde non découpé, API HTTP absente) la map est montrée telle quelle. Capture : `godot --path game -s res://tools/zone_shot.gd -- --out=z.png [--fail=1]`.

### Zones de classe et blocs (C.02e)

Deux découpes de plus dans `WorldAssets.compute_zoned`, sans changer le protocole ni l'API HTTP (ce sont des zones comme les autres dans `zones.json`).

- **Zones de classe** : les squelettes `1-<classe>-*` de l'os joueur (`families.json`, `_bundle_class`) et les skins de création de chaque classe (têtes et corps de `heads` / `bodies` dont `breed` est la classe, plus les skins de ses deux looks) quittent la base. Zone `class_<breeds.id>` (`WorldAssets.CLASS_PREFIX`), sans map (`maps: []`, absente de `ContentZones.lookup`). La base garde l'os de repli 666 et les bundles génériques (`1-combat`, `1-static`...). `ZoneStreamer.class_zone / class_ready / missing_zones(map, classes)`.
- **Qui les demande** (`ZoneGate`) : `characters` (écran de choix) et `map_enter` sont retenus jusqu'à ce que les zones des classes qu'ils montrent soient installées (le `map_enter` lit `actors[].breed` des joueurs, dont soi) ; un `actor_add` d'un joueur d'une autre classe lance le téléchargement derrière, sans retenue (`observe`), et `class_installed(breed)` fait redessiner les vues de cette classe (`ClientSession._on_class_installed`, métadonnées `breed` / `look` de la vue) ; l'aperçu de l'écran de création attend `class_installed` (`CharacterCreationScreen.class_gate`).
- **Blocs** : une zone qui ajoute plus de `zone_max_bytes` (150 Mo) à la base est coupée en deux, récursivement, selon le grand côté de la boîte des coordonnées de ses maps (`world_map`, `coords` de `worlds/<id>/maps/<map>.json`), jusqu'à tenir, n'avoir qu'une map, ou ne plus s'alléger (monstres répétés dans chaque bloc). Ids `<zone>-<n>` ; le bloc qui contient `start_map` est celui de la base (`start_zone`).

### Équipement et monstres à part (C.02g)

Deux zones de plus, toujours dans `zones.json` (le protocole HTTP ne change pas ; l'index gagne deux champs facultatifs).

- **Zone `equipment`** (`WorldAssets.EQUIPMENT_ZONE`) : les skins des objets que le monde distribue (boutiques, quêtes, recettes : `_gather_items`) quittent la base ; ceux que lâche un monstre restent dans la zone de ce monstre (mettre les drops de tous les monstres dans `equipment` la ferait passer à 3,4 Go). Sans map ; son entrée d'index porte `skins` (les ids de skin) pour que le client sache quand la demander. `ZoneStreamer.equipment_zone / equipment_ready / needs_equipment(looks)`. `ZoneGate` la demande derrière, sans retenue, quand `observe` voit un look qui porte un de ces skins (`actor_add`, `actor_look`, joueurs d'un `map_enter`) et quand l'inventaire s'ouvre (`ZoneGate.ask_equipment`, appelé par `ClientSession`) ; `equipment_installed` fait redessiner les vues des joueurs (`SessionLink._on_equipment_installed`).
- **Zone `<zone>-m`** (`MONSTER_SUFFIX`) : quand une sous-zone à couper pèse plus que `zone_max_bytes` et que ses monstres font plus de la moitié de ce poids (ou plus de la moitié d'un bloc : chaque bloc les répéterait), leurs fichiers vont dans `<zone>-m` (sans map) et chaque bloc de la sous-zone la **requiert** (`requires` dans l'index, `ContentZones.validate` vérifie que l'id existe). Les blocs ne répètent plus les monstres. `ZoneStreamer.requires_of` ; `missing_zones`, `zones_to_fetch` et `ensure` mettent les zones requises avant le bloc. La sous-zone de départ n'a jamais de zone `-m` (ses monstres restent dans la base avec son bloc).
- **Zone `<zone>-c<n>`** (`COMMON_SUFFIX`) : mesure sur `dofus` : la zone `10-1` (458 Mo) ne pesait pas par ses monstres (4 Mo) mais par 279 PNJ répartis sur ses 39 maps, les mêmes looks partout : une coupe ne l'allège pas. Quand une coupe n'allège plus (>= 95 %), `_split_into` sort ce que les deux moitiés demandent toutes deux (`_shared_entry`) dans une zone commune, si cela fait au moins le quart de la zone, puis recoupe sans elle ; les blocs la `requires` (jusqu'à 4 zones requises). `_ref_with` ajoute les fichiers d'une zone requise à la référence de la différence.
- APPROX(C.02g) : `<zone>-m` se télécharge en bloc à la première entrée dans la sous-zone (aucune mise en attente des monstres un à un) ; un skin que le monde ne distribue pas (commande `give` de l'admin) n'est dans aucune zone.

### Écran de chargement (C.03)

Après le `login_ok`, `LaunchScreen` ouvre `client/world_load_screen.gd` (`WorldLoadScreen`) : la liste des mondes du serveur (nom, taille, version, ce qu'il reste à télécharger), un bouton par monde (Jouer / Télécharger / Reprendre / Mettre à jour), une barre de progression (fichier n / N, octets, vitesse, temps restant), Annuler, Réessayer, Retour. Toute la logique est dans `client/world_loader.gd` (`WorldLoader`, sans Node) : `refresh()` (liste + manifeste de chaque monde comparé au cache `user://worlds/<id>/`, statut `current` / `new` / `partial` / `update`), `install(id)` (espace disque vérifié avant le premier octet, puis `ContentClient.download` : seulement ce qui manque, reprise par `Range`), `cancel()`, `launch(id)` (`ContentSource.use_world` : seulement quand le cache est complet). L'écran exécute ces appels bloquants dans un `Thread` et n'affiche que des champs du modèle ; les tests les appellent directement en pompant un vrai serveur du même processus. Après une coupure (`progress.json` présent), `ContentClient.verify_cache` recalcule le SHA-256 des fichiers installés (le reste du temps la taille suffit) et supprime ceux qui sont abîmés. L'API de contenu est sur le port de jeu + 1 (le défaut de `--http-port`). `client/disk_space.gd` (`DiskSpace`) lit l'espace libre via `dir` / `df` (Godot n'a pas d'API). Capture : `launch_shot --address=… --login=… --pick=<monde> --slow=1 --shot1="2|a.png"`.

## Console GM, sanctions et audit (A1.01a)

`admin_cmd{cmd, args}` est traité par `sim/world_admin.gd` (`WorldAdmin`) : le rôle (`PlayerActor.gm`, donné par l'hôte : le joueur local en standalone, le compte du serveur) est vérifié dans la sim, hors combat. Réponse : `admin_result{cmd, args}` (valeurs, jamais du texte : les phrases sont dans `ChatPanel.ADMIN_TEXTS`) ou `error`. `ProtocolAdmin` (comme `ProtocolParty` : `protocol.gd` est plein) porte les messages (`admin_result`, `announce`), les erreurs `banned` / `muted` / `kicked` et `USAGE` (l'aide `/help`).

- **Sanctions par compte** : `sim/sanctions.gd` écrit `sanction {ban, mute_until}` dans le document du compte (`Persistence`), sans toucher à `auth` ni à `bank`. Contrôles : `AuthService.login` / `resume` (après le mot de passe), `GameSession._hello`, `CharacterRoster.can_select` / `create`, `WorldChat`. Un ban n'expulse que les sessions du monde où la commande est lancée (`kick_player`) ; un joueur connecté dans un autre monde reste jusqu'à sa déconnexion.
- **Expulsion** : `WorldSim.kick_player` met l'erreur en dernier événement et ferme la session (même mécanisme que « connecté ailleurs ») ; `GameSession.kicked` prévient l'hôte, `ServerHost` ferme la socket après `KICK_GRACE_MS` (la fermeture immédiate perdait la raison) et ne parque pas la session. `NetBackend` lit les paquets restants quand la socket est fermée.
- **Audit** : chaque commande, refusée ou non, passe par `WorldAdmin._record` : mémoire (`audit_log`, 200) et `audit_sink` (posé par l'hôte via `LocalServer.audit_sink`). Le serveur écrit `server/admin/audit_log.gd` (une ligne JSON par commande, `--audit-log=<fichier>`).
- Ajouter une commande : un `match` dans `WorldAdmin._run`, une ligne dans `ProtocolAdmin.USAGE` et `ChatPanel.ADMIN_TEXTS`, un test dans `tests/test_admin.gd`.

## Métriques d'administration (A1.01b)

`GET /admin/metrics` sur le port HTTP (`--http-port`), avec `Authorization: Bearer <jeton admin>`. Le jeton admin est un secret du propriétaire du serveur (`--admin-token=` ou la variable `SUPERDOFUS_ADMIN_TOKEN`), distinct des jetons de session : un jeton de session n'ouvre pas `/admin/*` et le jeton admin n'ouvre pas l'API de contenu. Sans jeton configuré, la route n'existe pas (404). `ServerHost._route` envoie `/admin/*` à `server/admin/admin_api.gd` (`AdminApi`), le reste à `ContentApi`. `server/admin/metrics.gd` (`ServerMetrics`) mesure la durée de chaque `ServerHost.poll` (fenêtre de 600 ticks : moyenne, max) et lit les sims : `{version, protocol, uptime_s, connections, players, maps_active (maps avec au moins un joueur), fights, worlds{id: players, maps_loaded, maps_active, fights}, tick{count, window, avg_ms, max_ms}, memory_bytes}`. Test : `tests/test_admin_metrics.gd` (deux clients `NetBackend`, un combat, jetons).

## Admin web (A1.02a)

Le tableau de bord est `http://<ip>:<http-port>/admin` (page statique `server/admin/web/index.html`, sans secret : elle demande le jeton admin, le garde dans `sessionStorage` et l'envoie en `Authorization: Bearer`). Le jeu et l'admin partagent le port HTTP ; l'export embarque la page (`include_filter="*.html"`). Routes (toutes sauf la page exigent le jeton) : `GET /admin/overview` (métriques + joueurs connectés + combats en cours + nombre de comptes), `/admin/accounts?q=` (recherche par compte ou nom de personnage), `/admin/account?login=` (fiche : rôle, création, dernière connexion et adresse, ban / muet, coffre, personnages), `/admin/character?world=&name=` (le document du personnage : vivant s'il est connecté, la sauvegarde sinon), `/admin/audit?limit=` (derniers événements d'abord), `POST /admin/action` (corps JSON `{action, ...}`). `AdminViews` lit, `AdminActions` agit. Les actions de jeu (tp, give, kamas, level, heal, kick, ban, unban, mute, unmute, say) passent par `WorldAdmin.run_web`, qui exécute la même commande que la console GM sous le GM transitoire `web-admin` et la journalise de la même façon ; `password` (`AccountStore.set_password`), `save` et `reload` sont journalisées par `AdminActions`. Jamais de hash, de sel ni de jeton de session dans une réponse, jamais de mot de passe dans l'audit. `HttpServer` lit maintenant un corps de requête (`Content-Length`, 16 Ko max, sinon 413) ; `HttpFetch.start_post` pour les tests. `AccountStore.note_seen` garde `{at, ip}` de chaque connexion dans le document du compte. Test : `tests/test_admin_web.gd`.

## Plusieurs mondes sur un serveur (S.04a)
Un serveur sert plusieurs mondes sur le même port : chaque monde ouvert est un `WorldSim` (`LocalServer.worlds`), le `hello{world}` d'une session la route vers le sien, donc aucun événement ne passe d'un monde à l'autre. `server/cluster/world_cluster.gd` (`ServerHost.cluster`) liste les mondes (`server_list` -> `servers`, côté joueurs : seulement les ouverts), les ouvre (`start`, avec construction du paquet de contenu) et les ferme (`stop` : joueurs sauvegardés et prévenus par `error{world_closed}`, monde retiré de l'API de contenu). L'admin y accède par les actions `world_start` / `world_stop` et `GET /admin/worlds`. L'écran de chargement lit `players` dans `/worlds`. Instances (S.04b) : `world_create{id, content, name?}` / `world_remove{id}` (admin) font un monde `amis` qui lit le contenu d'un autre (`incarnam`) : `LocalServer.instances` + `WorldSource.instance()` (mêmes données, `info.id` = l'instance, `info.content` = le contenu), donc sauvegardes, listes et personnages à part ; `instances.json` du dossier de sauvegarde, rouvert au démarrage (`WorldCluster.restore`). `welcome.world`, `characters.world` et `servers[]` portent `content` ; l'API de contenu liste l'instance sous son id (`content`) et sert le paquet du contenu ; le client (`WorldLoader.content_of`) met en cache et lit par contenu. Supprimer une instance garde ses personnages sauvegardés.

## Sécurité du serveur (S.05a)
`ServerHost` ne fait confiance à aucun client : un seau à jetons par connexion (`server/security/rate_limiter.gd`, 60 messages de rafale puis 30 / s) renvoie `error{rate_limited}` et coupe (1008) après 20 refus d'affilée ; au plus 16 connexions par adresse ; un seau par adresse pour `login` / `register` / `resume` (le hachage coûte ~0,1 s) ; trame > 64 Ko = coupure 1009. Les valeurs sont des `var` de l'hôte (`rate_burst`, `max_per_address`, `auth_burst`…) et des APPROX(S.05). L'API de contenu ne sert que les hachages du manifeste, jeton obligatoire. `tests/test_security.gd` contient le fuzz des commandes (tirées de `SCHEMA`). S.05c : le hachage des mots de passe tourne dans un thread (`AuthJob`), `chat_send` / `admin_cmd` ont un seau par session (`Conn.costly`), et une adresse coupée 3 fois en 10 min est bannie 10 min (`AddressPenalties`).

## Standalone vs serveur (frontière du code commun)

Le but : un maximum de code commun. **Toutes les règles** (combat, IA, XP, craft, quêtes, HDV, échanges, guildes…) vivent dans `sim/` et `shared/`, et tournent telles quelles dans les deux modes. La roadmap (`docs/ROADMAP.md`, lots P0.02 puis S.*) détaille la mise en place.

| | Standalone (`api/`) | Serveur (`server/`, Godot headless) |
|---|---|---|
| Règles, IA, combat | `sim/` (le même code) | `sim/` (le même code) |
| Transport | appel direct (`LocalBackend`, JSON aller-retour) | WebSocket JSON (`NetBackend` côté client) |
| Comptes et sessions | un compte local implicite | authentification, jetons, reconnexion, une connexion par compte |
| Persistance | `FilePersistence` (`user://saves`) | `DbPersistence` (SQLite, puis Postgres), transactions |
| Multijoueur | bots ou plusieurs clients dans le même process (tests) | vrais joueurs |
| En plus | — | limitation de débit, audit, admin/GM, plusieurs mondes et instances |

Règles de conception, à respecter dès maintenant :
- La sim reçoit ses dépendances **injectées** : `Persistence` (`sim/persistence.gd`), `Clock` (`sim/clock.gd`) et une seed. Elle n'ouvre jamais de fichier en écriture, de socket ou de base, et ne lit ni `Time` ni `OS`, ni le RNG global. Seule exception : `DataFiles` lit les données statiques du jeu. Tout cela est vérifié par `test_architecture`.
- **`Persistence`** : des documents JSON dans des collections (`characters` : `<monde>/<nom>`, `accounts` : `<compte>`), avec `load_doc`, `save_doc`, `delete_doc`, `list_keys` et `commit(writes)` (écritures groupées, transactionnelles en base). Les appels sont synchrones : SQLite est en process, et une base distante serait derrière un cache côté serveur. La sim reste donc simple et déterministe.
- **Connexion** : l'hôte authentifie un compte (standalone : le compte local `local`) et crée une `GameSession` par connexion (`sim/game_session.gd`). `hello{world}` ouvre le choix du personnage (`characters`), puis `create_character` / `delete_character` / `select_character` (règles dans `CharacterRoster` : look construit et vérifié par `LookBuilder`, classes créables envoyées dans `characters.breeds`, noms `namingrules`, uniques par monde sans tenir compte de la casse, 5 par compte et par monde). `hello{world, name}` joue directement ce personnage, en le créant au besoin avec les mêmes règles (outils, tests). Le serveur (S.01/S.02) créera la même `GameSession` pour chaque WebSocket.
- **Sessions** : `GameSession` appelle `connect_player(nom, look, compte)`. Le personnage garde son compte propriétaire. Un personnage ne joue que dans une session à la fois : une nouvelle connexion termine l'ancienne (`error{msg: connected_elsewhere}`, puis `WorldSim.take_closed`).
- **Persistance du serveur (S.03)** : `server/persistence/ServerPersistence` (même interface que `FilePersistence`) écrit atomiquement (tmp relu puis renommage), garde les 10 dernières copies de chaque document dans `<save-dir>/_backups/` (au plus une par 5 min, une de plus à la suppression), relit un document illisible depuis sa dernière copie valide et sait `restore`. L'hôte sauvegarde tous les personnages connectés toutes les 5 min (`ServerHost.autosave_ms`) en plus de la sauvegarde à la déconnexion. Options : `--autosave=<min> --backups=<n> --backup-interval=<min>`.
- **Hôte** : `LocalServer` = un `WorldSim` par monde, plus la `Persistence` et la `Clock` partagées. Plusieurs `LocalBackend` peuvent partager un même `LocalServer` (tests multijoueurs, bots). Le serveur réseau (S.01) enveloppera ce même `LocalServer`.
- **Serveur réseau (S.01)** : `game/src/server/server_host.gd` (`ServerHost`) enveloppe un `LocalServer` : `TCPServer` + un `WebSocketPeer` par connexion, une trame texte = un message JSON, un `GameSession` par connexion, `poll(delta)` lit les commandes, fait avancer le serveur, puis envoie ce que chaque session a produit. `main.gd` (script `SceneTree` qui ajoute le nœud `ServerApp`, X.01 : un serveur exporté ignore `-s` et ouvre `scenes/server/server.tscn`, voir `docs/EXPORT.md` ; `ContentSource.set_dev_root` déplace la racine des données à côté de l'exe), `godot --headless --path game -s res://src/server/main.gd -- --server --port=7777 --world=dofus --save-dir=<dossier>`) ne fait que lire les arguments, brancher `FilePersistence` et `SystemClock`, et appeler `poll`. Le client s'y branche par `api/net_backend.gd` (`NetBackend`, un `GameBackend`) : `ClientSession` ne sait pas lequel il a. `ping{t0}` / `pong{t0, server_ms}` sont les seuls messages du transport (répondus par `ServerHost`, jamais par la sim) ; le client en tire l'horloge du serveur. Une connexion refusée ou coupée devient `error{code: network}` côté client. Rien dans `sim/`, `shared/`, `client/` ou `api/` ne référence `server/` (`test_architecture`). Le contenu HTTP viendra sur un second port (C.02).
- **Comptes (S.02a)** : `game/src/server/auth/` (aucune notion de jeu) : `AccountStore` (collection `accounts`, clé = login, section `auth` : sel + hachage SHA-256 itéré, rôle), `AuthService` (jeton de session de 32 octets, une connexion par compte), `PasswordHash`. `ServerHost.auth` posé (c'est le cas de `main.gd`, sauf `--no-auth`) : une connexion doit envoyer `register{login, password}` ou `login{login, password}` ; la réponse est `login_ok{token, role, login}` ou `login_error{code}`, et la `GameSession` est alors créée avec le login comme compte (`CharacterRoster` y rattache les personnages). Tout autre message avant `login_ok` : `error{not_logged_in}`. Le jeton sera exigé par l'API de contenu (C.02). Le standalone n'a pas de compte.
- **Reconnexion (S.02b)** : une coupure sans logout (tout code de fermeture sauf 1000, que `NetBackend.close()` envoie) parque la session dans `ServerHost` et son jeton reste valide `AuthService.park_ttl_ms` (10 min). Un combattant reste dans son combat (`WorldResume.detach`, `PlayerActor.detached`) : `Fight.set_absent` lui fait passer ses tours, puis `FightAI` joue pour lui après `Fight.ABSENT_GRACE_MS` (60 s) ; hors combat rien n'est gardé (sauvegarde, libération). `resume{token}` (ou `login` avec le mot de passe) rend la session : `resume_ok{state}` puis `GameSession.resume()` rejoue welcome / stats / inventaire / quêtes et le combat en cours (`fight_start`, `fight_begin`, `fight_turn`) ou la map. Une connexion silencieuse depuis `ServerHost.idle_ms` (20 s) est remplacée par `login` / `resume`, sinon `already_connected`. Détails : « Reconnexion (S.02b) » dans les Découvertes de la roadmap.
- **Reconnexion automatique (S.02c)** : `NetBackend.auto_reconnect` : après une coupure (connexion avec compte, pas `close()`, pas 4001 / 4003) il passe en `reconnecting`, émet `net_reconnecting{attempt, delay_ms}`, réessaie après 1, 2, 4, 8 s puis toutes les 8 s et envoie `resume{token}` en premier ; `resume_ok` termine, `bad_token` abandonne. Côté client, `SessionLink` (dans `ClientSession`) affiche `ReconnectBanner`, oublie combat et fenêtres à `resume_ok` (le serveur rejoue l'état) et renvoie à `LaunchScreen` (avec `notice`) quand le lien est perdu pour de bon.
- **Plusieurs joueurs sur une map (P3.01)** : `MapInstance.broadcast` envoie `actor_add` / `actor_remove` / `actor_move` / `actor_look` à tous les joueurs de la map ; un nouvel arrivant reçoit `map_enter` avec les présents. Ce qu'un joueur apprend d'un autre est sa **fiche publique** (`PlayerActor.to_dict` : id, nom, case, direction, look, marche en cours, `breed`, `level`, `life` si fantôme), liste blanche `PlayerActor.PUBLIC_KEYS` testée dans `tests/test_players.gd` ; compte, kamas, caractéristiques, inventaire et quêtes ne partent que vers leur propriétaire (`player_stats`, `inventory`, `quest_list`). Les joueurs se traversent. Un joueur en combat n'est plus un acteur de la map. Côté client, `client/other_players.gd` (`OtherPlayers`) affiche nom, infobulle et menu clic droit des autres joueurs.
- **Chat (P3.02a)** : `shared/chat.gd` (`Chat`, règles pures) : canaux `general` (la map ; en combat, les combattants du combat), `team` (le combat), `commerce` et `recruitment` (tout le monde), `private` (un joueur), et `group` / `guild` / `alliance` réservés (`channel_unavailable`, lots P3.03 / guildes) ; raccourcis et noms de canaux = table `chatchannels` (`/s`, `/b`, `/r`, `/w`, `/t`, `/g`, `/a`, `/p`). `chat_send{channel, text, to?}` : la **sim** analyse le texte (`Chat.parse` : `/b vends`, `/w Bob salut`, faute de frappe = `unknown_command`, jamais envoyée à tous), le nettoie (caractères de contrôle, 256 caractères) et applique l'anti-flood (`Chat.flood_wait` : 5 messages / 10 s, commerce et recrutement 1 / 60 s, APPROX(P3.02) : pas de constante dans les données). `WorldChat` (`sim/world_chat.gd`) route vers les destinataires et répond `chat_msg{channel, from, from_id, text, at, to?}` (le privé est aussi renvoyé à l'expéditeur) ; un joueur absent ou soi-même = `player_offline`. Rien n'est persisté ; `WorldChat.log` garde les 200 derniers messages (modération, console A1.01). Le chat passe aussi en combat (avant la garde `in_fight` de `WorldSim._handle`). Client : `ChatPanel` (fenêtre à onglets Général / Privé / Commerce / Recrutement, en bas à gauche ; Entrée donne le clavier à la boîte ; les mots sans canal, comme `/tp`, restent des commandes GM via `CommandLine.parse`) et `ChatBubble` (bulle 5 s au-dessus du personnage qui parle en général). Le texte d'un joueur est échappé avant d'entrer dans le BBCode. Test : `tests/test_chat.gd` (règles, routage, combat, journal, et le même flux par deux `NetBackend`).
- **Groupes (P3.03a)** : `shared/party.gd` (`Party`, règles pures : 8 membres, le chef est le premier, exclusion, commandement), `shared/protocol_party.gd` (`ProtocolParty` : `party_*`, extension de `Protocol`), `sim/world_party.gd` (`WorldParty`, un `WorldHandler` : invitations (60 s), `party_update` par destinataire envoyé quand il change, suivi du chef à la téléportation, départ à la déconnexion). Pas de persistance : un groupe dure autant que ses membres sont connectés. Le bonus d'XP vient de `FightRewards` (nombre de joueurs du combat). Client (P3.03b) : `client/party_frame.gd` (`PartyFrame` : cadre, invitations, menu des membres, marqueurs sur la map), alimenté par `ClientSession._dispatch` ; invitation depuis le menu d'un joueur (`other_players.gd`).
- **Amis, ennemis, ignorés (P3.05a)** : `shared/contacts.gd` (`Contacts`, règles pures sur un livre `{friends, enemies, ignored}` d'entrées `{account, name}`), `shared/protocol_contacts.gd` (`contacts_get`, `contact_add`, `contact_remove`, `contacts`, `contact_status`), `sim/world_contacts.gd` (`WorldContacts` : stockage dans le document de compte via `Persistence`, notices de connexion aux amis, `ignores(listener, speaker)` utilisé par `WorldChat`). Test : `tests/test_contacts.gd`. Client (P3.05b) : `client/contacts_model.gd` (listes, commandes de chat `/friend /enemy /ignore` et `/un…`), `client/contacts_window.gd` (`ContactsWindow`, touche F : trois onglets, pastille en ligne, chuchoter, retirer, ajout par nom), menu d'un joueur (Message privé, Ajouter en ami, Ignorer) ; la sim ne transmet plus les invitations de groupe et d'échange d'un joueur ignoré (silence, comme le chat). Test : `tests/test_contacts_client.gd`.
- **Échange entre joueurs (P3.11a)** : `shared/trade_rules.gd` (`TradeRules`, règles pures : lignes `{uid, qty}` normalisées, offre vérifiée contre le sac, les objets portés et la bourse, poids), `shared/protocol_trade.gd` (`ProtocolTrade` : `trade_invite / accept / decline / set / ready / cancel`, `trade_invited / open / update / end`, erreurs `trade_busy`, `not_in_trade`, `no_trade_invitation`), `sim/trade_session.gd` (offres et validations d'un échange), `sim/world_trade.gd` (`WorldTrade`). Flux : invitation (60 s, même map, ni combat ni fantôme ni fenêtre de PNJ ouverte, un seul échange par joueur), `trade_set` remplace l'offre et annule les deux validations (le sac de l'autre doit pouvoir la porter : `overloaded`), `trade_ready` revérifie les deux côtés (objets toujours dans le sac, non portés, kamas, poids des deux sacs) ; à la double validation les deux personnages sont écrits en **un** `Persistence.commit` (tout ou rien) puis `trade_end{done}`. Fins : `cancelled`, `moved` (`teleport`), `fight` (début de combat ou rejoindre), `disconnected`, `action` (toute autre commande d'un joueur en échange), `failed{code}` (refus au dernier moment, rien n'a bougé). Chaque échange ouvert laisse une entrée d'audit (`WorldTrade.log` et `sim.admin.audit_sink`, `cmd: trade`). Rien n'est persisté hors des personnages. Test : `tests/test_trade.gd` (règles, flux, annulations, sac plein, et le même flux par deux `NetBackend`). Client (P3.11b) : `client/trade_model.gd` (`TradeModel`, sans nœud : invitations, offres confirmées, messages construits depuis la dernière offre confirmée, textes des fins), `client/trade_window.gd` (`TradeWindow` : offre à gauche, celle de l'autre à droite, sac en bas, double-clic = poser / reprendre, Valider / Annuler ; fermer la fenêtre annule), `client/trade_invites.gd` (cartes Accepter / Refuser sous le cadre de groupe, 60 s) ; entrée « Échanger » du menu d'un joueur ; test `tests/test_trade_client.gd`.
- La sim est **multi-session dès le départ**. Tout message est adressé à un joueur (`_send(pid, ev)`) ou diffusé sur une map ou un combat. Aucune hypothèse « un seul joueur ».
- La sim fait **autorité** : chaque commande est validée comme si le client trichait.
- Les informations cachées (invisibilité, pièges adverses, inventaire des autres) sont filtrées par destinataire **dans la sim**, pas dans le client.
- Les données partagées entre joueurs (HDV, banque de compte, guildes, maisons) passent par `Persistence` avec des opérations atomiques. En standalone elles sont triviales, mais l'interface est la même.
- Les traces JSONL (`sim_cli`, `tests/scenarios/`) sont le contrat : elles doivent donner les mêmes événements via `LocalBackend` et via `NetBackend` (lot S.07).

## Géométrie Dofus (`shared/map_geometry.gd`)

- Une map compte 560 cellules : 40 rangées de 14, avec les rangées impaires décalées d'une demi-cellule.
- Numérotation : `cellId = row * 14 + col`.
- Chaque cellule a aussi des coordonnées « losange » (`to_iso`), les mêmes que celles de `IsoGrid`. On s'en sert pour l'écran (`to_screen`), l'orientation (`facing`, numérotée comme `DofusAnimNames.Direction`) et l'A*.

**Maps.** Les éléments d'une map Dofus 3 sont des sprites (`gfxId`) avec une affine, une teinte (0x80 = neutre) et un matériau :
- trois couches : fond, triés par `cellId` puis `innerCellRenderOrder`, et premier plan ;
- repère Unity centré sur la grille, y vers le haut, converti par `maps.py` : `écran = (x + 580,5 ; 419,25 − y)`, avec la cellule 0 en (0, 0).

`addons/dofus_renderer/map/DofusMapNode` les dessine. Le fond passe sous tout le reste. Les éléments triables vont dans le nœud y-trié partagé avec les entités, avec une clé de tri juste sous la rangée des pieds. Le premier plan passe au-dessus de tout.

Le seul mode de fusion supporté est le multiply `(DstColor, OneMinusSrcAlpha)`, par un shader qui respecte l'alpha. Ne sont **pas encore rendus** : les animations de shader (vent, rotation, translation, couleur animée, distorsion, dissolve, émissif), les particules, le post-process et les « staging sequences ».

**Sorts.** `spells.py` convertit chaque effet en `{kind, target, min, max, duration, area, cond}`. Les masques de cible donnent l'équipe (`A` = ennemis, `a`/`g` = alliés, `C` = lanceur) et les conditions (`*E<état>` / `*e<état>` : le lanceur est / n'est pas dans l'état ; sans `*` : la cible). Les variantes « porté » (`K`) sont ignorées. Les bits de `m_flags` codent : 1 = en ligne, 4 = ligne de vue, 8 = case libre, 16 = case occupée, 64 = portée modifiable. Le niveau contient aussi `criticalEffect`, `criticalHitProbability`, `minCastInterval`, `maxCastPerTarget` et `statesCriterion`. Les formules officielles (XP, prospection…) sont dans la table `luaformulas`.

Les visuels viennent des scripts du client (`spellscripts`, type 1) : `animId` (→ `AnimAttaque<id>`), `casterGfxId`, `targetGfxId`/`targetGfxId2` (os FX, animation `FX_<dir>`), `missileGfxId`… Les effets simulés sont listés dans la section Combat.

**UI.** L'interface de Dofus 3 est en UI Toolkit : UXML et USS dans `uielements_assets_all.bundle`. Les propriétés USS y sont des ids `StylePropertyId`, pas encore décodés ; les mises en page actuelles sont donc approchées, avec les vraies textures et polices.

## Mondes (plusieurs expériences, un seul moteur)

Un monde est un `WorldSource` :
- `get_info()` renvoie `{id, name, start_map, start_cell, wander_ms}` ;
- `get_map(id)` renvoie un `MapData` ;
- `get_spawns(id)` renvoie `[{looks: [...]}]`.

Les implémentations disponibles :
- `JsonWorldSource` lit `game/worlds/<id>/world.json` et `maps/<id>.json`, en chargement paresseux. Le monde `test` compte 3×3 maps et est généré par `tools/gen_test_world.gd`, avec une seed fixe ; les JSON sont modifiables à la main. Le monde `incarnam` (P1.07) : les 50 maps extérieures d'Incarnam (`maps.py world incarnam --center 154010373 --area 45`, voisins réels, `mapscrollactions` prioritaire) plus 24 intérieurs reliés par 49 portes (P1.07b : maisons, Mine en 7 salles, Taverne et cave ; `jondo.py`) ; les groupes de monstres sont composés par la sim (P1.09), `monsters.json` liste les monstres de chaque sous-zone.
- `WorldSource.from_dicts(...)` crée un monde directement en code, ce qui sert pour les tests.
- **À venir** : un `DofusWorldSource` qui décodera les vraies maps du client Dofus. Il se branchera sans toucher ni la sim ni le client.

Pour choisir le monde, utiliser `ClientSession.world_id` (export, `incarnam` par défaut) ou `hello{world}`. Les tests utilisent `test` (généré) et `tests/fixtures/spells.json` : ils ne dépendent pas du contenu extrait.

## Recettes

- **Ajouter un message** :
  1. une constante et un builder dans `Protocol` ;
  2. un handler dans `WorldSim.handle` ;
  3. un `match` dans `ClientSession._on_event` ;
  4. un test dans `tests/test_sim.gd`, qui passe par `LocalBackend` comme le client.
- **Ajouter une mécanique serveur** (combat, PNJ, objets) : la coder dans `sim/`, avec des données dans `shared/` si le client en a aussi besoin. Le client, lui, ne fait qu'afficher les événements. S'il a besoin de prédire, il réutilise `shared/` au lieu de dupliquer le code.
- **Ajouter une IA** : l'écrire dans `sim/ai/`, en fonction statique pure `(acteur, map, now, rng)`. Elle tourne à l'identique en standalone et sur le serveur.
- **Brancher un serveur** :
  1. Écrire `api/remote_backend.gd` : un WebSocket qui envoie `JSON.stringify(cmd)` et émet `event` pour chaque message reçu. `time_ms()` renvoie l'horloge du serveur, estimée à partir de `welcome.time` et du ping.
  2. Le serveur v1 est un Godot headless (`SceneTree` script) qui possède un `WorldSim`. Pour chaque socket, il appelle `connect_player`, `handle` et `drain`, puis `tick()` à pas fixe.
  3. Un serveur natif plus performant peut ensuite réimplémenter la sim dans un autre langage. Il sera validé en rejouant les traces JSONL de `sim_cli`. Le projet Dofus3+/Jondo est un **test indépendant** : ne pas supposer de lien avec lui.
  4. Dans `ClientSession._make_backend()`, choisir `LocalBackend` ou `RemoteBackend`. C'est le seul endroit à modifier.
