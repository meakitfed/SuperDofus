# SuperDofus — guide pour agents

Ce projet est un client de jeu façon Dofus 3 écrit en Godot 4.7 (GDScript, renderer `gl_compatibility`). Il affiche les vraies entités Dofus grâce à `game/addons/dofus_renderer`, et le même moteur peut servir plusieurs mondes.

**Le client ne parle qu'à une API** (`GameBackend` : `send`, signal `event`, `time_ms`). Cette API se branche de deux façons :
- sur la logique de jeu embarquée (`LocalBackend` → `WorldSim`), c'est le mode **standalone**, celui d'aujourd'hui ;
- sur un **serveur** qui exécute le même `sim/`, plus tard.

Tout ce qui « serait côté serveur » va dans `game/src/sim/`, jamais dans le client. Lire `docs/ARCHITECTURE.md` avant de toucher au gameplay.

## Workflow de session : la roadmap
Le plan complet (recréer toutes les fonctionnalités de Dofus, par priorité) est dans **`docs/ROADMAP.md`**, découpé en lots d'une session.
**Toute feature doit marcher aussi en mode serveur** : un test via `NetBackend` (127.0.0.1) accompagne chaque nouvelle mécanique ou message ; sinon dette notée au Journal.

**Phase M (multijoueur)** : la phase M de la roadmap (plan : `docs/PLAN_SERVEUR.md`) passe avant les lots de contenu P2.xx (en pause). Ne rien mettre de spécifique à Dofus dans le code de session, réseau, comptes, contenu, admin.
- `/suite` fait avancer d'un lot : choix, implémentation, vérification, puis mise à jour de la roadmap.
- `/suite plan` présente seulement le plan du prochain lot.
- `/suite P1.05` cible un lot précis.
- `python tools/roadmap.py status | next | show <ID> | set <ID> todo|doing|done|dropped | check`.

En fin de session, même sans `/suite`, si du travail touche un lot : mettre à jour son statut, le Journal et les Découvertes, puis lancer `roadmap.py check`.

## Règles (vérifiées par `tests/test_architecture.gd`)
1. `shared/` et `sim/` : aucun `Node`, `Input`, rendu, ni référence à `client/` ou `api/`.
2. `client/` n'utilise jamais une classe de `sim/`. Il passe uniquement par les messages de `Protocol`.
3. Les messages sont des Dictionary JSON-safe. Faire `int()` à la lecture, car les nombres reviennent en float après JSON.
4. Toute nouvelle mécanique a son test de scénario dans `tests/test_sim.gd` ou `tests/test_fight.gd`, piloté via `LocalBackend`.
5. Côté client, un événement qui s'anime (un sort, par exemple) est une séquence : `FightView.handle` renvoie `true` et émet `sequence_done` à la fin. Les événements suivants attendent.

## Pièges connus
- Nouveau message : constante + entrée `SCHEMA` + constructeur dans `protocol.gd`, puis régénérer `docs/PROTOCOL.md`. Nouvelle erreur : une constante `E_*`, ajoutée à `ERROR_CODES` et à `client/error_texts.gd`. Les règles renvoient des codes, jamais du texte.
- Heredocs bash + Python : les caractères accentués sont corrompus, et les antislashs aussi (`\n` devient un vrai saut de ligne). Écrire les scripts de patch dans un fichier (outil Write) avant de les lancer.
- Maps : les ombres utilisent un multiply qui respecte l'alpha (shader dans `DofusMapNode`). Le MUL brut de Godot fait apparaître le RGB aléatoire des pixels transparents DXT.
- Un sort lançable est un **grade** (id = 1 000 000 + `spelllevels.id`), pas un `spells.id` : le grimoire, les variantes et la barre parlent en `spells.id`, les combats en grades (`SpellBook.grade_for`).
- Les sorts Pandawa ont des variantes Sobre/Saoul (`cond`) : les conditions se lisent **au moment du lancer** (sinon un état posé par le sort déclenche aussi l'autre variante).
- Le disque C: est presque plein : extraire le contenu en `--webp` et vérifier l'espace libre avant toute grosse extraction.
- `game/content/` contient les assets Ankama : ils ne doivent jamais être commités.
- Pas de `print` ni de `push_warning` par frame ou par sprite, cela coûte des centaines de ms.
- Les clip groups Godot ne s'imbriquent pas et dessinent en noir sur un fond transparent.
